## Connected behavior and lifecycle

Create uses the existing email-only operation and shows confirmation only after validated success. Resend/revoke retain the existing confirmation dialog and original version/key preparation. A current summary must match before opening a confirmation; repeated actions cannot replace it. A confirmed trainer mutation stays busy through its automatic fresh summary read. This closes the transient idle handoff found by the first native run. List failures are unavailable, never successful empty results; pending, expired, revoked and accepted statuses remain distinct. A confirmed result does not promise that its historical status remains current.

Acceptance discovery uses entry/explicit summary refresh and explicit Recheck active clients. There is no new server listener, polling mechanism or real-time acceptance claim. Returning through native Back or Back to Clients changes a scope-owned navigation refresh version, replacing the roster destination store and forcing a fresh clientsEmulator read even during rapid interrupted transitions. A navigation result contains no reply, email, bearer or roster row. Neither an acceptance reply nor a safe summary is inserted into the roster. Pending/revoked invitations remain separate from active assigned clients; accepted membership must pass the existing current authorization and projection.

UI callbacks bind the captured UID/workspace/epoch and confirmation key before reaching the shared owner, so queued old fields/dialogs cannot act on a newer scope or confirmation. Retired form Create events are also rejected after a confirmed result. Duplicate Clients navigation is fenced by the existing destination model; duplicate owned invitation entry and Back are guarded in typed Navigation 3. Keys remain UID/workspace/trainer/role/authority-epoch bound. Workspace/account/epoch loss clears the existing invitation projection and fences replies. Leaving trainer presentation cancels/fences its callback and clears draft, confirmation, summaries and local delivery presentation. Root disposal also clears transient state and refuses subsequent enter/leave calls. No bearer enters navigation or saved state.

Cancellation does not erase prepared critical work or stop native receipt settlement. The original UID/key/payload/version is retained in the existing protected command slot; ambiguous, rejected or unsettled mutation outcomes still block clean departure. Original-key retry remains reachable through the root recovery surface after authority loss and through Clients invitations/recovery when authorized. The original acceptance link is still process-only and must be explicitly reopened after process death. Trainer-only settlement no longer requests a redundant membership-root replacement; acceptance settlement still requests fresh verification. No receipt grants access, no unresolved work is discarded, and no new recovery framework is added.
