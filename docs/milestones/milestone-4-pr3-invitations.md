# PR 3 local invitation procedure and fixture policy

Production invitation operations remain disabled. No provider, delivery domain, expiry, normalization or cap proposal has been approved for release. `invitationEmulator` repeats the PR 2 guard before service acquisition: both project variables, when present, must name `demo-tillfailure-m3`, and Auth and Firestore emulator endpoints must be explicit loopback hosts. Release hosts inject no product Firebase client. No deployment is part of this change.

## Version 1 emulator fixtures

- Auth Emulator email/password accounts exist before invitation creation. Creation resolves the canonical email to an Auth UID; acceptance binds **both that UID and the lowercased, trimmed-before-submission email**. The trusted endpoint rejects whitespace in submitted addresses, reads fresh Admin Auth user records, and requires a non-disabled, verified caller and inviter. It never treats a submitted email, mobile profile, cached verification flag or possession of a link as proof. Provider linking and first-time production registration remain policy gates.
- Lifetime is exactly 48 hours from server creation/resend time, with token versions starting at 1. These values are fixtures, not approved policy. Caps reuse PR 2: two account catalog contributions and five active workspace roster members. Suspended memberships and catalog contributions remain distinct as in the existing lifecycle primitives.
- The emulator uses a 30-per-UID/server-minute admission quota for new commands and successful read operations, plus a separate 120-request budget covering replays and well-formed rejected attempts. Matching, freshly authorized and validated receipts bypass the smaller admission quota; they still consume the independent request budget. Mutation admission and its receipt commit in the same transaction. Neither local limit is an approved production abuse policy.
- Only the active workspace owner trainer can operate invitations. Listing returns the newest 20 summaries. Preview requires the matching verified Auth UID/email and returns workspace name, stable IDs, pending status, version and expiry. It creates no account or membership.

The create/resend response returns one cryptographically random 256-bit token **once**; the response represents an entry of the form:

```text
https://invite.tillfailure.invalid/i/<invitation-id>/<version>#<token>
```

The local-delivery UI keeps the bearer out of visible/selectable text and offers **Open local test invitation** to hold it in process memory. This is manual in-app entry, not an associated-domain/Universal Link implementation. `.invalid` is a reserved test domain, not a registered product delivery domain. The token is never placed in a navigation key, saved state, summary, receipt, audit, analytics or log. No email is sent. Do not retain raw callable responses or screenshots of the local-delivery token as evidence. Dismiss the local link after testing.

For an unverified fixture, verify it in the Auth Emulator/operator test setup and use **Recheck access**, then preview. No real verification/invitation delivery provider is selected. The intended link stays only in process memory through sign-in, verification and controlled wrong-account departure. After process restart the user must reopen the original link.

## Retry, rotation and concurrency

Every mutation carries one UID-bound command key. The receipt stores a hash of the full request (only a hash of token material) and a secret-free historical result. Changed payload/key reuse is rejected. A matching create/resend retry confirms the committed command but cannot recover its token; explicitly resend with the current version and a new key to obtain another local link. Resend rotates token/hash/version and resets expiry. All old links fail immediately. Expired pending invitations may be explicitly resent or revoked; accepted/revoked invitations cannot be reopened.

Accept, resend and revoke read the same internal invitation and version inside a transaction. Exactly one live transition wins; retries observe the winning state. Two accepts with the same caller/key produce one commit and a replay; a different key loses. A receipt replay rechecks current Auth/account/workspace/inviter authority, and acceptance replay additionally rechecks the exact active client membership. A historical receipt is never a fresh role grant.

Before native mutation issuance, one safe command record is atomically saved in the existing encrypted UID envelope. It contains command kind/key, workspace/invitation IDs, version and creation email where needed, **no token**. Native issuance and clean-departure freeze share a lock. Pending/ambiguous commands block departure, including after process death and destination recreation. Transport cancellation suppresses presentation while native settlement still resolves the protected record. Auth UID/generation fences reject late callbacks. A network/timeout/malformed-response/storage-settlement failure retains the command for same-key retry; a conflicting receipt retry also remains blocked until the original request is recovered. Only a validated matching success or receipt clears it. Every error—including quota exhaustion, missing/disabled identities, permission denial and conflicting payloads—retains mutation work and is ambiguous about the original outcome. A rejected retry or instantaneous receipt absence cannot rule out an earlier invocation committing later. Permanent loss of authorization leaves recovery blocked pending a separately approved trusted reconciliation policy; no negative receipt/discard path is implemented. There is no discard/repair shortcut. Reopening the original link supplies the transient token for a restored pending acceptance.

## Pending acceptance entry ownership

Parse and validate entry candidates before changing retained invitation memory. Once acceptance is durably prepared, process memory protects the original UID, command identity, invitation ID/version and transient bearer under the platform ownership lock. A different invitation, changed version, invalid entry or different bearer for a known original is rejected without replacing the retained link or protected command. Both manual Open and local-delivery continuation use the same guard and read current protected work; an unreadable ledger fails closed. Native preparation captures the issued bearer before transport, covering issuance outside the UI thread.

On first metadata-only restoration, clear any link opened before the owning UID/ledger was known, even if its ID/version matches: safe metadata cannot verify its bearer. The caller must explicitly reopen the original entry after restoration. Later metadata refreshes for the same protected command preserve its existing process link.

Same-process root recreation reuses the protected transient link. Disposed roots ignore further events; pending links are readable/consumable only by their owning UID, and existing native UID/generation fences remain in force. A process restart restores only safe command metadata, so retry requires explicitly reopening the original ID/version entry. No bearer enters the encrypted envelope, navigation, state diagnostics, logs or evidence. Matching reentry preserves the original command key; only verified settlement permits clean departure. The original entry must be retained by the caller outside the application if process death occurs.

## Atomic authority boundary

Android attaches a freshly refreshed ID token from the official Auth SDK to a bounded, no-redirect, emulator-only HTTP request implementing Firebase's [published callable protocol](https://firebase.google.com/docs/functions/callable-reference). The Android Functions SDK's incidental Instance ID lookup rejected the demo Firebase options before issuing any request during native testing; the narrow protocol transport avoids selecting a messaging/Instance ID service. Apple uses the official Firebase Functions SDK on the hosted Firebase app. Both report allowlisted errors and treat transport/decoding failures as unknown mutation outcomes. Unexpected backend exceptions are redacted internal callable failures and keep protected work unresolved; only known operation rejections are definitive.

The trusted transaction validates fresh caller/inviter Auth, active schema-current account/workspace/owner trainer, immutable path identities, trainer profile/directory/entitlement, bounded roster and contribution consistency, internal invitation and summary agreement, version, binding, expiry and receipt. Acceptance additionally rejects every existing target membership/profile/reference, validates the client's existing account/entitlement and bounded membership directory against the authoritative membership collection group, rejecting retained assigned-program headers, and uses the existing lifecycle counter projection. In one commit it bootstraps a missing client account, creates membership/minimal onboarding-pending profile/directory, updates entitlement/workspace counters and revision, consumes the invitation, updates its summary and creates the receipt. It never repairs or reactivates conflicting/disabled/revoked records. Account Auth creation is an external fixture prerequisite, not part of Firestore atomicity. Auth checks occur immediately before the Firestore transaction; Auth and Firestore do not offer a joint transaction.

`invitations`, `lifecycleCommands`, `invitationRateLimits` and `invitationRequestLimits` remain Admin-only under default-deny Rules. The summary writer uses an allowlist: schema, invitation ID, masked email, client role, status, expiry/creation/last-send timestamps and non-secret token version. Exact gets enforce the allowlist and path-bound active trainer authority. Direct collection lists and mobile writes are denied. The trusted callable runs the bounded ordered query and validates every returned summary against the strict projection allowlist; one malformed summary rejects the entire list. The list uses the existing single-field `createdAt` index; no composite index is needed by this measured query. Terminal hashes/receipts are retained in the disposable emulator dataset; production retention/deletion must be approved separately.

The invitation reply only triggers the existing gate's fresh Auth and server account/membership reads. Client access ends at `MembershipVerifiedFeaturePending`; onboarding, health data, full home, offline grants, real delivery and PR 4 remain outside this slice.
