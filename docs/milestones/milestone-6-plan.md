## Canonical scope and intended outcome

[Roadmap milestone 6](../implementation-plan.md#6-exercises-and-program-creation) is **Exercises and program creation**: a trainer browses system/custom exercises and creates and publishes an immutable program-template version. [Product scope](../product-scope.md), [schema](../firestore-schema.md#exercises-and-programming), [security](../firestore-security.md) and [design inventory](../design-inventory.md#section-to-product-map) agree. No milestone rename or conversation-derived replacement is needed.

The complete intended outcome is a reusable trainer-authored program with ordered workouts/exercises and validated prescriptions, whose published version cannot change when a later draft is edited. This plan proposes four sequential end-to-end slices, starting with browsing useful exercise definitions. The first PR does not complete the milestone. Search, media, autosave and archive details in designs/proposals are not implicit requirements or permissions for that PR.

Program assignment and account-owned snapshots remain M7; active workouts/logging/offline recovery M8; review/progress M9; scheduling M10; messaging M11; production/privacy/release hardening M12. M5 is [merged but not fully accepted](milestone-5-closeout.md). Its unresolved gates remain open with the dependencies in that closeout.

## Proposed data and authorization contracts

### PR 1 read contract

Keep `systemExercises/{exerciseId}` server/admin-owned. Create-only synthetic fixtures contain only schema version, stable ID/path, name, normalized name if needed by existing schema, bounded muscle/equipment labels, plain-text instructions and status. No client identifiers, notes, health guidance about a person, media links or private audit payload. Proposed engineering ceilings: name 120 Unicode scalars, instructions 2,000 scalars/8,000 UTF-8 bytes, at most eight muscle and eight equipment labels of 40 scalars each. Freeze canonical validation/type/Unicode vectors in PR 1; reject malformed records instead of silently truncating them. These are fixture validation ceilings, not approved production taxonomy or size policy.

Return project-owned typed list/detail models, never SDK snapshots. List uses `status == published`, document-ID ascending, `limit(21)` for 20 rows plus lookahead. Navigation carries only a validated ID; detail performs a fresh authorized point read. Continuation binds the current UID/feature visit/query in transient state and uses the last displayed ID, not a cached snapshot. IDs are non-sensitive catalog identity, not confidential roster anchors or grants. Reissue the same authorization-constrained query on every page. Deduplicate by ID; refresh restarts traversal. No name ordering, full scan/local filter advertised as search, total count or traversal-wide consistency promise. An archived/removed item can disappear between pages; unavailable/denied/malformed is not a successful empty result. Malformed pages fail atomically without a partial list or false end.

Use server-source reads on both native SDKs with no cache fallback. The existing Rules evaluate account/entitlement on each server request. The trainer entry also requires a currently verified selected trainer shell, but the catalog's global Rules deliberately do not require that particular workspace: another active contribution can sustain entitlement. Test final-contribution loss and loss of only one of several contributions separately. Never make workspace membership or cached entitlement a substitute for the fixed global predicate. No direct Rule grant changes are expected for PR 1; if the exact query needs an index, demonstrate it before proposing the smallest source change in the implementation PR. This documentation task changes neither.

Direct Firestore reads return whole readable catalog documents. A typed mapper is not field-level security. Therefore the catalog must contain only globally eligible, client-safe exercise content; no hidden trainer/private fields may be stored there. Additional sensitive metadata would require a separate protected document, with its own approved requirement. Seed/admission validation and adversarial fixture tests enforce this constraint.

Catalog data stays transient under the current native memory-cache/session policy. Clear pages/details and cancel/fence callbacks on background, known authority/connectivity loss, UID/workspace/role/epoch/visit retirement and departure. Reopen/reconnect re-verifies before fresh reads. Unknown remote revocation is not instantaneous local erasure. Existing pending commands still block clean departure; browsing must neither replace nor settle them.

### Conditional custom, draft and publication contracts

These contracts are recommendations pending D5–D8, not existing grants. Proposed mediators verify a fresh non-anonymous bearer, enabled verified Auth and current schema-bound account/workspace/exact trainer membership before each operation; derive the caller from Auth, never a body UID. A system-exercise selection also requires current catalog entitlement. Custom-source selection requires the same author/workspace boundary as its read. Unknown fields, malformed sources and mismatched identity fail closed:

| Resource | Ownership/access and validation | Concurrency/recovery/lifecycle |
|---|---|---|
| `workspaces/{wid}/exercises/{eid}` | Immutable workspace/author/stable ID; active verified author account and exact active trainer membership in an active workspace on every read/write/replay. Plain exercise definition fields only; no client/health/private notes/media. Require exact supported schema, safe path IDs and approved field/size/taxonomy bounds. No cross-workspace or other-author access by ownership shortcut. | Explicit create/correct with expected revision, one revision advance, no last-write-wins. Same-key replay returns one decision. Archive, if approved, excludes new selection while already-published copies remain immutable; no hard delete/reference cascade. Decide return/restoration policy before enabling it. |
| Proposed `workspaces/{wid}/programTemplates/{tid}` and fixed `drafts/current`, with bounded workout/item children | Author-only source metadata/draft; immutable tenant/owner; revisions and ordered stable item IDs. Header/currentVersion pointer separate from draft revision. A saved draft may be incomplete but must satisfy structural/type/budget safety; publication requires complete semantic validation. Exact child layout/read/write byte budgets are PR 3 deliverables, not an existing schema. | Online explicit Save replaces only the expected draft revision atomically, including bounded removed children. Failed/conflicting Save preserves submitted original work; reload is explicit after terminal settlement. Same-account two-device edits can conflict even with one trainer. No silent merge, autosave or background upload. Unsubmitted draft clears under approved D6; server draft reopens via fresh authorization. |
| Existing proposed `programTemplates/{tid}/versions/{vid}/workouts/{workoutId}/exercises/{itemId}` | Immutable trainer-only publication, ordered workouts/items, copied approved exercise text/prescriptions, source identity/provenance and canonical content hash. No client access to any ancestor/descendant through assignment IDs. No client target, schedule, assignment or client profile in M6 publication. | Read expected draft/template revision, exact referenced exercise definitions and all authority before writes. In one bounded commit create version + complete children + command receipt and advance currentVersion/version counter/template revision plus the shared draft revision used to serialize Save/Publish. Same-key replay cannot create a second version; distinct keys at the same expected revision yield one winner and a durable conflict. Publication never rewrites old versions or assignments. |

For publish, the multi-document invariant is concrete: an advanced current pointer must never reference partial/mutable children. A narrow trusted transaction is proposed because it must validate the complete bounded source, derive the hash and commit all children/pointer/receipt together. Ordinary CRUD is not automatically routed through Functions: PR 1 uses Rules; PR 2/3 mediator proposals are justified specifically by exact durable decisions and recovery after authority loss. If a smaller Rules-based write design can prove the same approved outcome, review it before selecting; the existing generic journal has not proved that result.

Freeze finite ceilings before PR 3/4: total workouts/items/children, text/payload bytes, request/envelope bytes, reads/writes including authority/receipt/config/admission, retry count and elapsed work. Use at most three transaction attempts and a five-second elapsed-work check as an initial engineering bound, without claiming cancellation of an outstanding RPC. For publication count at least `workouts + items + version + template-update + draft-revision-update + receipt`, plus any additional audit writes actually chosen; separately count source reads and serialized/index bytes. Reject oversize before partial work. Existing resolver descriptors have an 8,192-code-unit bound: measure the **whole** new descriptor rather than assuming a large program fits. If an exact recoverable Save cannot fit, reduce the approved first draft cap or return for a concrete protocol decision. No automatic chunking, pointer-only descriptor to mutable content, second journal, blob store or generic recovery expansion.

An exercise edit/archival racing Save/Publish must be serialized by reading its revision/status in the same transaction. Freeze the copied content/hash at publication; later source corrections do not mutate it. Save versus Publish on the same draft must conflict through a common revision, with explicit reload/reconfirmation instead of publishing a silently newer draft. Missing/foreign/malformed source, authority loss and service failure are nonterminal errors, not manufactured conflict receipts. No raw Admin bypass, delayed trigger or UI check substitutes for current authorization or atomicity.

## Protected-command and departure compatibility

The baseline protected variants are invitation **create, resend, revoke, accept**, **onboarding completion**, **basic-profile update**, **client-membership revocation**, and **trainer-note Save**. Keep their original keys, per-kind canonical hashes, legacy forms, positive/conflict outcomes and own-resolution behavior unchanged. Assignment/booking namespaces are not part of this inventory.

PR 1 adds no protected variant or durable record. PRs 2–4, only after D8, must add narrowly typed adapters to the existing one-command slot/resolver, with explicit versioned canonical descriptors, strict minimal receipts, atomic effect/receipt and whole-key fences. Recheck live business authorization for execution/replay. Own resolution may require only eligible original global identity and exact binding; it grants no template, workspace or content access. New kinds must participate in writer/coverage/provenance audit before issuance is enabled. Preserve receipts/fences/config together; no TTL, history reset or reused fixture keys.

Persist exact original payload/key/revision before transport; block replacement while unresolved. Resolve confirmation durably stops normal retries; generic errors, absent legacy history or expired authority never settle work. Store full validated terminal proof before retirement; preserve note `compacted-v1` marker semantics and all seven legacy forms. Choose new-kind settled retention explicitly under D8; do not automatically retain full draft text or silently extend the note-only marker approval. Unknown older decoders lock rather than discard. Test pending/proof/retired states, late duplicate callbacks and same-key contradictions across all eight existing variants whenever shared protocol code changes.

Clean departure remains freeze → prove all critical work empty → drain SDK writes → durable UID marker → fence/dispose → Auth sign-out → SDK terminate/clear and proven local cleanup → pin/marker completion → new generation. A new feature cannot bypass it, create an independently hidden queue or expose A's drafts/content/callbacks to B. Storage/key/schema/history or identity uncertainty remains locked; no new support/discard/export or role-restoration escape.
