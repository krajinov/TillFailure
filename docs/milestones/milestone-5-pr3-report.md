## Trusted source, authorization and revision contract

The new guarded `basicProfileEmulator` handles `profile-get` and `update-profile`. Every invocation, including replay, reloads verified enabled Admin Auth and checks active schema-current account/email binding and lifecycle revision, selected active workspace/counter shapes, exact active client membership/directory and valid completed workspace onboarding. Trainer and foreign callers are denied. UID is derived from Auth, never input. The update strictly allows only the three approved basics and expected global revision, workspace authorization context and original idempotency key. Both server and shared input reuse onboarding validators. No email or other protected field is updated.

A single transaction reads five fixed authority/source documents and the command receipt when applicable; at most three transaction attempts are allowed. Update touches only users/{uid}.displayName/locale/timeZoneId/profileRevision and its caller-bound receipt. It preserves unrelated account data, assignment, memberships/counters/entitlements and all workspace onboarding fields. A matching update increments the global profile revision exactly once. Concurrent same-key retries replay one decision; different saves at the same revision have one update and one conflict. Future/malformed revisions, records, extra fields, unauthorized callers and key reuse with a different request cannot partially write or repair data. The read returns only own validated basics/revision, and update returns only a minimal acknowledgment/rejection with workspace, status, revision, original command key and replay flag.

The prior plan preferred direct safe CRUD pending a proven recovery path. The current request explicitly requires an atomic fields/revision/idempotency receipt, so this narrow emulator mediator is justified by durable acknowledgment/rejection, not by a copied roster projection. Rules remain unchanged and continue denying mobile direct account writes, trainer global-account reads and enumeration. The native adapters use the existing protected transport and hard-coded new endpoint selection; no arbitrary callable/path/UID selector is exposed. Release hosts still inject no product Firebase client.

There is no stored name projection or fan-out. PR 1 reads the authoritative global name transactionally on every currently authorized roster/detail request. Existing provisioning and invitation acceptance create a blank account only when absent; existing accounts/names are preserved. Onboarding updates global basics and its selected completion atomically with expected global revision; replay does not revert a subsequent edit. Account lifecycle updates only status/lifecycle revision, while membership/workspace lifecycle preserves source basics. The new writer neither copies names nor changes any of those writers. Tests verify updated names through real authorized details in two workspaces, with unchanged workspace completion and denied direct trainer access. This is fresh-read behavior, not a traversal snapshot or continuous remote-update notification promise.

## Durable conflict and recovery semantics

The existing one-command encrypted UID registry gains an optional typed profileUpdate payload. Before transport, admission persists the exact normalized submitted fields, expected revision, UID, original workspace context and key. Other command variants reject that payload. Old invitation/onboarding envelopes remain compatible; future/unknown or damaged shapes lock rather than being overwritten. A legacy Swift request constructor is retained for existing harnesses/bridge callers. There is no second store/queue, persisted draft, silent replacement, discard, repair or new bearer material.

A stale command atomically records a caller/key/request-bound `profile-conflict` receipt without changing the account. That durable decision prevents the same original command from committing later. Only a strictly validated matching updated/conflict result settles this exact registry slot. Generic revision-conflict errors, transport/Auth/availability failures, malformed or foreign-key replies and settlement-storage failure retain the original work and block clean departure. The negative receipt is the narrow engineering resolution of approved explicit conflict reload; it does not relax G6 for other rejected or unreplayable commands. Revoked authority still prevents replay and can leave work locked under the existing unresolved-policy gate.

After definitive conflict settlement, the modified unsent draft stays visible and Save stays disabled until explicit reload. Replacing that draft requires the current confirmation; failed reload does not overwrite it. A successful read supplies a new revision, and only a subsequent explicit Save prepares a new key. Unknown-outcome retry always uses the original payload/revision/key, including after root/process restart or loss of the original destination. No new token-opening requirement is added for this token-free command. Existing invitation bearer secrecy remains intact.

## Shared experience and presentation boundaries

Client Profile offers Edit basic profile through typed Navigation 3. Trainers receive no edit control. A single root-owned Koin ProfileViewModel owns editor and recovery surfaces, immutable MVI state and navigation effects. Fresh reads supply initial/reload values; fields are bounded to existing onboarding limits. Loading/saving, validation, success, unavailable/retry, access-lost/recheck and conflict are distinct. The form explains global workspace scope and the trainer-visible name. Back and Home/Profile tabs require confirmation before losing a modified unsent draft. Submitted critical work remains reachable from Profile/Home and the identity recovery gate.

UID/workspace/authority epoch, distinct editor visit, current source destination and confirmation identity fence UI/navigation and late replies. Reopening advances the underlying Profile key too, preventing an old editor/disposal from matching the new visit. Scope loss/root disposal clear presentation and cancel/fence work while native receipt settlement continues. An explicit ON_STOP guard clears drafts/baselines and queued navigation even when lifecycle state collection pauses; the same authority epoch cannot reopen it before fresh verification. Drafts are transient and account-scoped; automatic background/scope retirement clears them. Submitted payloads remain protected in the existing registry.

Returning stays on the correct Profile destination. Only a fresh own-profile read can refresh its approved presentation fields, with matching UID/workspace/epoch and non-regressing profile revision. That event changes no role, workspace, authority, onboarding, server record or roster row and carries nothing into saved navigation. Invitation replies/receipts still cannot authorize or insert clients. No mutation is added to trainer details.
