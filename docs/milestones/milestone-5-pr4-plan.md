## What the current model actually distinguishes

| Operation | Actual representation and implementation | Meaning and limitation |
|---|---|---|
| End one trainer assignment | `workspaces/{wid}/clientProfiles/{clientUid}.trainerId` identifies one assigned trainer. Invitation acceptance creates it; no product unassign/reassign writer or independent relationship ID/status/revision exists. | Clearing/changing `trainerId` would not revoke workspace membership or its catalog contribution. It would also violate current profile validators. This operation is not implemented and is not the proposed PR 4 operation. |
| Revoke client workspace membership | Exact `workspaces/{wid}/memberships/{clientUid}` has `role=client`, `status=active|revoked`, revision and contribution flag. [Catalog lifecycle](../../firebase/functions/src/catalog.ts) supplies a trusted transaction primitive. | Removes this UID's access through this workspace membership, including all client content gated by it. There is no mobile relationship-revocation endpoint/UI today. The primitive's supplied `callerUid` is not authentication or authorization. |
| Archive a client profile | Broad schema/design text proposes archival, but the implemented minimal profile contains identity, `trainerId`, creation time and pending/complete onboarding fields only. | No implemented archive flag, archive writer, archive roster or archived-profile access policy. Hiding a row is not an access-control transition. PR 4 must not invent this meaning. |
| Disable global account | `users/{uid}.accountStatus` and `lifecycleRevision`, with `transitionAccountLifecycle`; Firebase Auth disable is a separate external step. | Denies all account-gated workspaces/catalog, rather than one relationship. Membership contribution counts are retained for correct lifecycle handling. Neither Firestore account disable nor Auth disable/delete belongs in this operation. |

The effective current client relationship is the conjunction of an active exact client membership, the workspace profile's assigned `trainerId`, active workspace and eligible accounts. PR 1's `relationshipStatus=active` is derived from membership; it is not a separately stored trainer-relationship state. Workspace `ownerUid` is distinct from membership role and profile assignment. The owner field alone grants neither PR 1 access to another trainer's clients nor permission to mutate lifecycle state.

There is one membership and one client profile per UID/workspace, with one role and one assigned trainer. The single-trainer MVP does not encode several independent trainer relationships within a workspace. It therefore cannot safely implement “end only this trainer's assignment while keeping a different trainer's relationship here.” Multi-trainer relationships, reassignment and role changes require a separate model/policy decision. Adversarial multi-trainer tests in PR 1 demonstrate isolation, not an approved multi-trainer product.

The same account can have independent memberships/profiles in other workspaces. Revoking `(workspace A, client U)` must not write U's membership, trainer assignment or onboarding in B, nor any other user's membership/account. U's global name/preferences, profile revision, account status, lifecycle revision, Auth identity and credentials remain unchanged. U's one global catalog entitlement necessarily changes by A's contribution; that is derived authorization maintenance, not global account disablement. Another active contribution can keep catalog eligibility. Global basic-profile editing remains possible through another eligible completed client workspace; an original command bound to A cannot be retargeted to B.

## Approved narrow MVP policy

**Approved by Josip, 2026-10-21:** immediate revocation of one exact client workspace membership, initiated only by the active workspace owner who is also the assigned active trainer. Preserve other memberships and global account data except the required catalog contribution adjustment. Reject targets with any retained assignment header or matching workspace assignment index; preserve records, grant no new former-trainer client/coaching-history access, and defer same-UID/same-workspace re-invitation. No account disablement, self-leave, owner override, Undo, archive or automatic restoration. Label the proposed UI action **Revoke client access to this workspace**, supporting pending-onboarding and completed client memberships within this approved boundary.

**Not accepted as finished behavior:** potentially indefinite Locked Recovery caused solely by membership loss after a command may have committed. Josip requested a resolution design first. The [own-command outcome protocol](milestone-5-command-resolution-design.md) is approved and implemented for emulator review; it must be accepted before revocation implementation and does not claim that all recovery failures disappear.

Evaluate initiators explicitly:

| Candidate initiator | Approved boundary for this slice | Reason / alternative |
|---|---|---|
| Assigned trainer | Only when also the active workspace owner | Assignment alone already grants narrow reads; workspace-wide access removal needs explicit authority. Allowing non-owner trainers would be a broader policy. |
| Workspace owner | Only when also this client's assigned active trainer | Matches current invitation administration without granting ownership-based access to unrelated clients. Owner override across assignments is deferred. |
| Client | No self-service leave in PR 4 | A distinct client-initiated leave policy could later use the same lifecycle arithmetic; it needs its own confirmation, pending-work and receipt-replay rules. |
| Trusted operator | No new operator revocation interface or impersonation path | The existing emulator provisioning operator is not blanket product revocation authority. Incident/reconciliation operations need separately defined authority and audit; administrative possession of the primitive does not approve them. |

The committed membership denial is immediately effective for subsequent server authorization evaluations. It cannot retract a response already authorized before commit or erase bytes on a disconnected device. Known loss closes presentation; foreground/reconnect repeats verification. Current product flows issue no offline grant and have no offline roster/profile view. No duration, scheduled effective date or remote-erasure promise is introduced.

There is no Undo or in-place reactivation in PR 4. Preserve the revoked membership as a tombstone and the minimal client profile/onboarding/provenance unchanged. Removing the discovery reference is the existing atomic lifecycle operation, not deletion of client/history data. The generic primitive can activate memberships, but it must not become a product restore endpoint or workaround for the tombstone.

**Approved first slice before assignment use:** reject a new revocation when either `users/{clientUid}/workspaces/{wid}/assignedPrograms` or `workspaces/{wid}/assignedPrograms` filtered by that target `clientId` contains any document, regardless of status. Both probes are within the selected workspace; assignments in another workspace are independent. Two bounded existence probes suffice; do not scan/cancel/archive assignments. This deliberate limitation handles the current trainer-index gap described below and keeps PR 4 independent of Milestone 7 retention/query redesign. It includes retained terminal artifacts, not only live programs. Supporting assignment-bearing clients would require a separate scope decision and enforcement plan.

**Re-invitation:** returning to this same UID/workspace is unsupported in the first slice. Existing acceptance already rejects any retained membership, client profile or directory, and rejects retained account-owned assignment headers. Keep those protections. A newly generated invitation token must not override them, and an old acceptance receipt must not restore membership. No “Invite again” or restoration promise is added. The existing email form can still create/resend a pending invitation whose later acceptance conflicts with retained state; its safe summary is not a guarantee of joinability. No automatic invitation cancellation or data cleanup is proposed to make it usable.

A future approved re-invitation needs a new explicit invitation and acceptance plus a reviewed relationship-generation/new-identity scheme. It must fence old commands and cursors, define onboarding reuse, and prove retained content cannot become readable when the UID/workspace path is reused. Current assignment Rules can reopen still-active, unexpired content after generic membership restoration; a fresh token alone does not solve that. Do not delete tombstones, reset revisions, revive old assignments or change `trainerId` to bypass the conflict. Joining a different eligible workspace remains independent under the existing invitation policy/caps.

**Historical access:** do not grant the former trainer a revoked-client roster/detail, name, profile or coaching-history view. Stored records remain present without a new read grant. The workspace owner can still see the existing masked invitation summaries under their independent invitation authority, including accepted/revoked invitation history; membership revocation does not rewrite an accepted invitation as revoked. Proposed own-command outcome permission is separate from workspace authority and returns no client/profile/history data. Future legal/history access remains a separate decision. No deletion, export, retention deadline or private reason is implied.

**Client experience:** retire the affected shell and show neutral access-lost/recheck guidance, or Locked Recovery while protected work is unresolved. The prerequisite must let supported commands obtain their own minimal outcome despite workspace authority loss, durably settle and then use normal clean departure; indefinite membership-loss-only lock is not the approved end state. Missing identity/binding or damaged storage may still block resolution. Do not show “account disabled,” expose a trainer's private reason, or force sign-out. With no remaining membership, a verified signed-in account reaches the existing workspace/no-access gate. With other memberships, explicit selection freshly verifies them; selected-workspace loss must not silently route elsewhere. Pending work keeps its original workspace/key.

### Why a rejected retry cannot clear unresolved work

Example: client U sends profile command K in A; the server commits its global fields and receipt, but the response is lost. Trainer revokes A. U retries K; the existing handler rejects current membership before returning the receipt. That rejection describes the retry's authority, not whether K committed earlier. The same ambiguity exists if an original invocation is still racing when a later invocation observes no receipt. A missing receipt at one instant, repeated rejection, timeout, transport cancellation or loss of the initiating screen cannot prove non-commit.

Keep the original UID, action, target/workspace, fields, expected revisions and key in the existing encrypted partition. Only a strictly validated matching terminal outcome can settle it; storage failure while settling retains the command. No permission error or target revocation is converted into a negative receipt locally. The baseline had no own-command resolver; the emulator prerequisite now adds a serialized not-applied fence and terminal-proof projection across the six variants, without changing normal business authorization or interpreting generic errors as negative decisions.

The current implementation can leave **Locked Recovery with sign-out/account switch blocked indefinitely**, even though another workspace remains usable through explicit fresh selection. Josip did not accept that as finished behavior when the sole cause is workspace authority loss. Damaged storage may block selection/resolution separately. Revocation must not wait for a client device to approve or acknowledge removal, and the trainer cannot clear that client's ledger. Do not restore membership just to retrieve a receipt, retry using a new key/workspace, or silently discard it.

**G6 prerequisite, protocol and emulator implementation approved:** review the [own-command resolution report](milestone-5-command-resolution-report.md) and prove its acceptance before revocation. Approved outcome permission depends on active original global identity/full command binding, not a workspace role. A resolver and normal mutation serialize on the same receipt path: a committed receipt returns a minimal historical decision; verified absence permits an immutable whole-key fence that prevents a delayed original from ever committing. Durable local proof precedes retirement of the original pending slot. Receipt-history coverage, legacy acceptance binding and unavailable identity/storage limits are explicit. No export, retention duration, destructive discard, privileged support override, enumeration or second recovery system is proposed.

### Prerequisite readiness

The product boundary and prerequisite engineering protocol are approved; the emulator prerequisite is implemented for review, and revocation is **not implementation-ready**. The prerequisite covers invitation create/resend/revoke/accept, onboarding and basic-profile update, plus consumed-key guards for every writer sharing `lifecycleCommands`. Future revocation must be the seventh protected variant. New covered-generation commands can use absent-receipt fencing only with preserved atomic receipt history; intact supported legacy receipts can be projected, but missing legacy acceptance binding or uncertain legacy absence stays protected. Membership loss alone must not deny supported own resolution. Broader identity/storage/legacy policy gates remain explicit and are not solved by restoration or discard.

## Proposed implementation contract after approval

### Trusted operation and preparation

1. Add a purpose-specific guarded emulator revocation operation through existing project-owned command/native transport boundaries. Derive caller UID from fresh verified/enabled Admin Auth; reuse named demo-project/loopback enforcement and current identity validators. Never accept caller UID, role, trainer identity, caps, arbitrary paths or a choice of next membership status as authority.
2. Check active schema-current caller account/email/lifecycle, active workspace, `ownerUid == caller`, exact active trainer membership, and valid existing trainer profile/directory. Require exact target client membership/path/profile identities and `profile.trainerId == caller`. Distinguish the caller's live authority from target eligibility: target account disablement need not prevent safe removal; no new catalog access or target account repair is allowed. Unsupported membership/profile shape or invalid count state fails closed, with trusted reconciliation left separate.
3. Existing roster/detail DTOs intentionally expose no lifecycle revisions. Add a narrow authorized prepare/read response for the confirmation's target and revision metadata. It returns no extra client identity/contact fields, account/entitlement snapshots or roster counts. Preparation performs no critical mutation and grants no later authority. Hide the action unless preparation proves eligibility; backend enforcement remains mandatory.
4. Bind the command to exact `workspaceId`, `clientUid`, expected target membership revision, expected workspace `membershipRevision`, expected caller membership and caller account lifecycle revisions, policy/command version and a fresh original key. Persist the original command before issuance in the same protected slot/freeze lock used by invitation/onboarding/profile commands. New revisions are obtained by explicit preparation after a definitively settled conflict, never silently substituted into an unresolved command.
5. Recheck all current authority, path/schema/relationship invariants and the two assignment presence preconditions in the mutation transaction. A new transition requires the target's active discovery reference; replay permits its expected absence after revocation. The profile has no independent relationship revision today: transactionally reading `trainerId` plus membership/workspace revisions is sufficient only because no reassignment writer exists. Any future assignment-of-trainer writer must advance shared relationship authority/fence old commands; this plan does not approve one.

### Atomic work and idempotency

Use `commandId(callerUid, originalKey)` and the existing `lifecycleCommands` namespace, with a distinct versioned revocation kind and canonical request hash binding caller, target, workspace, expected revisions and policy. Do not reuse the generic `membership-transition` receipt with an unchecked cast. Validate exact receipt/result shape, identity, revision ranges, command key, decision status and timestamp before replay or settlement. Receipts contain minimal decisions and revisions, not names, contact fields or profile snapshots.

The future revocation writer must participate in the prerequisite's consumed-key protocol: read that same receipt path in the effect transaction and perform no lifecycle writes if any fence, terminal receipt or unknown/conflicting record already consumes it. Its per-kind adapter must validate historical success/conflict without needing current workspace membership and return only the dedicated resolver's minimal fields. A generic error/absent read cannot settle the command.

Refactor/reuse catalog validation, counter projection and contribution logic **inside the same authorized transaction**. Calling `transitionMembership` after authorization in a different transaction creates a check/use race. Its replacement `set` currently drops `joinedAt` and `invitationId`; use a targeted status/contribution/revision update for this new operation, preserving provenance and every unrelated membership field. Keep existing primitive callers/tests compatible; do not broaden its product surface.

All reads precede writes. For an authorized new command with matching expected state, one commit performs exactly these five business writes:

1. Update only target membership to revoked, contribution false and next revision.
2. Delete only the target workspace's minimal discovery reference.
3. Update only target catalog count/status and next entitlement revision using the existing strict arithmetic.
4. Update only selected workspace membership revision and the two counters.
5. Create the immutable caller-bound success receipt.

Leave the global account, client profile/onboarding, other memberships/directories/entitlements, invitations and assignment artifacts byte-identical. No audit free text or external side effect is required. Any added audit/admission write must be explicitly budgeted and reviewed; it cannot determine whether authorization committed.

For a stale new command, recommend PR 3's **durable negative-decision pattern**: after current caller/resource authorization, atomically create only a matching `revocation-conflict` receipt with bounded observed revisions and no lifecycle writes. Serialize it on the same receipt/source reads so every concurrent invocation of this exact key either sees the success or the immutable conflict; it cannot later mutate. A target already revoked by a different key is a conflict, not fabricated success for this command. Reload/reconfirm uses a new key only after matching conflict settlement. Generic denial, malformed source, assignment-bearing precondition failure, missing receipt, throttle and availability errors retain the prepared command; they are not conclusive rejection receipts. UI preparation reduces these cases but cannot eliminate races.

Bound work independently of history: at most 12 fixed authority/source/receipt paths, the existing bounded active-roster consistency check with `limit(B+1)` at fixture B=5, and two `limit(1)` presence probes (target account-owned headers; exact workspace indexes filtered by target `clientId`). Conservative ceiling: 20 returned source documents per attempt, at most three attempts, with a five-second Firestore-work deadline after fresh Auth. No assignment descendants, invitation history, all-workspace traversal or per-client fan-out. Validate finite configuration/read/serialized-byte/index-write budgets before enablement and recheck during work; overflow or deadline returns no partial result. This is a proposed ceiling to prove, not a claim that current primitives enforce it or that any 20 MiB request fits Firestore limits. Prove exact queries/default indexes in emulator tests; the checked-in assignment `workspaceId` collection-group override is not a blanket query authorization/index guarantee. No index deployment is authorized.

At the normal business endpoint, success/negative receipt replay happens **after current caller authorization but before new-transition revision/active-target preconditions**. The implemented prerequisite own-outcome endpoint instead requires current original global identity and exact command binding, not workspace membership; it only projects a terminal decision or fences that key. It never executes a business mutation, supplies a business replay DTO, restores access or claims current membership state.
