# Milestone 4 plan: identity, invitations, onboarding, and role-aware shell

Status: **planning proposal; PR 1 emulator implementation evidence is in [the PR 1 report](milestone-4-pr1-report.md). Product-policy approval remains separate.**
Baseline: `9f67d44` (PR #3 merged into `main`; inspected on clean `milestone_4` checkout, 2026-10-03)

## 1. Current baseline and reusable primitives

- Both hosts still launch the temporary Foundation Home/Details Navigation 3 flow. The debug-only design catalog has nonfunctional authentication, client-home, and trainer-dashboard compositions. Its sign-in and role controls are fixtures, not product behavior. Shared MVI uses immutable state, `onEvent`, buffered effects, `FeatureRoute`/`FeatureScreen`, lifecycle-aware collection, destination-owned Koin ViewModels, typed serializable keys, and the approved design tokens/components.
- ADR-001 accepted official Firebase Android and Apple SDKs behind TillFailure interfaces. `shared/androidMain` has a guarded emulator `AndroidFirebaseSpikeClient`; `iosApp/FirebaseNativeBridge.swift` and `shared/iosMain/IosFirebaseBridge.kt` exercise a narrow Swift callback bridge. Both prove Auth observation, document reads/listeners/writes, source and pending-write metadata, stable errors, cancellation, UID/epoch callback fencing, and terminate/clear/recreate. They are demo-project spike clients, **not** production Auth or app composition wiring. The hosts do not yet inject a product Firebase bundle.
- `firebase/functions/src/catalog.ts` already contains bounded, revision/receipt-backed membership, workspace, and account lifecycle transactions. Assignment and booking primitives also exist. `firebase/functions/src/index.ts` exposes only booking spike callables; invitation, provisioning, product Auth and onboarding endpoints do not exist. The current Rules allow published system-catalog reads, account-owned assigned-content reads, trainer assignment-index reads, and `spikeEcho`; the default deny still applies to product account, workspace, membership, profile, invitation-summary, and invitation-internal paths. The current indexes are membership collection-group `userId,status` and planned-workout collection `status,scheduledInstant`; invitation/roster discovery indexes are not present.
- The encrypted, atomic, UID-partitioned recovery envelope and same-process SDK generation repair are useful for account isolation. They do not implement the complete sign-out protocol, a product offline grant, or workout reconciliation. `RecoveryUidContract` accepts the wider Firebase UID string domain, while raw Firestore document paths in the existing lifecycle code require one safe segment; the two contracts must not be confused.
- The [Milestone 3 report](milestone-3-report.md#verification-ledger) records its own attributed evidence: final backend/Rules 95/95, Android host 63/63, API 34 connected 73/73, shared iOS 63/63 from an earlier execution, and a signed Swift harness with 144 PASS lines. These are **historical Milestone 3 results**, not Milestone 4 runs or a claim that every suite was rerun at PR #3 merge. Older roadmap/spike descriptions and earlier totals must not be used as the current implementation inventory. The Xcode app has no test target; Kotlin iOS tests do not execute Swift Firebase implementations.

## 3. Data, authorization, and navigation flow

**Authority:** Firebase Auth identifies the UID and verified-email state. Trusted Functions repeat caller, account, workspace, membership, invitation and revision checks because Admin SDK bypasses Rules. Firestore Rules independently gate mobile reads/writes through active account, active workspace, current schema and exact membership role/identity. `users/{uid}/authorizations/systemCatalog` authorizes only global catalog reads, never a workspace role. A local role or grant authorizes **zero server requests**. An Auth token that is valid while the Firestore account is disabled must still be denied. Product account/profile/membership Rules must be added explicitly; default deny remains for every unimplemented path.

**Records:** `users/{uid}`; fixed `users/{uid}/authorizations/systemCatalog`; `workspaces/{wid}` with owner, membership revision, roster/contribution counters; `workspaces/{wid}/memberships/{uid}`; minimal trainer/client profiles; Admin-only `invitations/{iid}` containing token hash/version/email binding; trainer-readable, secret-free `workspaces/{wid}/invitationSummaries/{iid}`; and deterministic `lifecycleCommands/{id}` receipts. Existing raw UID paths are retained under the provisioning constraint above. A first verified client Auth identity may bootstrap only its own active account and inactive, zero-count entitlement through a trusted idempotent command; this creates **no** workspace or role. The internal invite is never mobile-readable. Create/resend/revoke/accept update the internal authority and summary atomically where the transaction permits; external email send follows committed state with safe retry and never decides membership. Add only the exact indexes required by measured membership discovery and invitation-summary queries; the current membership group index exists, while `status,createdAt desc` invitation-summary index is planned. Rules are not query filters: test both `get` and constrained `list`.

**Online root transition:** `Launch → RestoreIdentity → ServerAccountAndMembershipCheck → {Auth, IdentityUnsupported, WorkspaceGate, WorkspaceChoice, TrainerProvisioningPending, InvitationPreview, Onboarding, ClientShell, TrainerShell, AccessLost}`. While checking, show loading without protected cached content. Zero eligible memberships gives WorkspaceGate with invite entry or operator-provisioning pending status; the app can only recheck membership after the operator acts. One eligible membership routes according to server role/onboarding state; more than one gives WorkspaceChoice. An expired Auth session attempts SDK refresh online; if refresh fails, route to Auth while keeping account-owned recovery locked. `permission-denied`/disabled/revoked is AccessLost, not an offline fallback; while no offline grant exists, `unavailable` routes to `ConnectToVerify` or Locked Recovery when unresolved data exists. Retry re-runs the server check. Role change or revocation observed by listener/foreground recheck fences callbacks and replaces the full role stack and scope.

**Invitation transition:** Native Android intent/iOS URL callback supplies a bounded, syntactically validated HTTPS link to the shared coordinator. It retains only an opaque, short-lived token reference in memory while Auth restores, the user signs in, or an invited client creates an Auth identity; no protected preview is shown from cached token data. A process restart requires reopening the link. Online preview returns a minimal allowlisted workspace/inviter/expiry DTO after rate limiting; it grants no membership. Accept requires the same current verified-email account, active account/inviter/workspace, pending unexpired matching token version, caps and supported schemas. Use the current Admin Auth user email/verification state rather than trusting a client-supplied email or stale profile copy. One transaction consumes the token, creates the client membership/minimal profile, updates workspace roster and UID entitlement, summary and receipt. Same caller/key retry resolves the committed outcome; competing accepts produce one winner. Wrong-account linking waits at an account-switch gate. Used/revoked/expired/mismatched tokens show nonrevealing failure and a safe resend/contact route. Clear the pending token after terminal success/failure; never persist it in a NavKey or recovery envelope. A post-auth deep link resumes preview only after online revalidation. Other deep links remain deferred; forged or unauthorized destinations resolve to a safe root.

**Onboarding and shell transition:** The accepted membership may have `onboardingStatus=pending`; a server-validated minimal profile completion command advances it once with a receipt/revision. The route survives restart by loading server state. Duplicate submit and timeout reconcile by receipt/server read. A trainer enters only after operator provisioning and a fresh server membership check; neither host calls the privileged command. The shared Navigation 3 root replaces Auth/invite/onboarding stacks after current membership verification; role-specific minimal shell destinations are selected from that server result. The normal shell is never chosen by a timer or cached role. If a user changes selected membership, recheck the target online, dispose the prior workspace scope, and rebuild the root. Unavailable offline shows `ConnectToVerify` or Locked Recovery, not an ordinary role shell.

**Offline and departure:** Milestone 4 issues **no** `OfflineAccessGrant`: the duration is unapproved and no downloaded workout exists. Offline startup shows `ConnectToVerify`, or Locked Recovery for unresolved account-owned data; neither state opens protected content. Future restricted workout access requires both approved duration and verified downloaded content. Known revocation locks protected navigation and retains unsynchronized records under the departing UID. PR 1 implements only the clean-departure subset of [the canonical protocol](../offline-sync.md#safe-sign-out-and-account-switch-protocol): freeze, prove no critical work, drain any SDK writes, fence callbacks, sign out Auth, terminate/clear Firestore, prove account-local cleanup, dispose scopes, then clear a persisted switch marker and permit another account. Failure or interrupted cleanup stays locked. PR 5 adds pending-work synchronization and recovery handling; destructive discard remains disabled without approval. No account-scoped bytes or callback may enter another account graph.

Keep spike harness opt-in. Use `AuthFixtureScreen` only as visual guidance, never its fake callbacks.

Reuse the existing membership collection-group `userId,status` index; add another index only if the exact tested query needs it. No new product callable is required.
- **Responsibilities/platforms:** Common domain models the gate and retryable vs denied failures; data maps Auth/Firestore source metadata; MVI owns loading/submit/retry and one-shot navigation. Android native SDK and Apple Swift bridge implement real emulator sign-in/sign-out/session observation and server-source reads. Both hosts initialize/inject the emulator-only product test client; no debug fixture may reach a release backend by accident.
- **Clean-only sign-out contract:** Freeze new account operations; inspect the app-owned journal/upload registry and protected account partition and require **no pending or unresolved critical work**; then require `waitForPendingWrites` to succeed while new writes remain frozen. Unknown inventory, timeout, offline pending write, or unresolved recovery payload cancels departure, keeps Auth unchanged, and offers stay/retry without discard. Once clean, persist a UID-bound `SwitchingOut` marker **before** changing Auth; failure to persist blocks sign-out. Cancel listeners/jobs, advance the UID/epoch fence, sign out Auth, terminate Firestore, clear its persistence, remove only proven disposable account-local state, dispose the account Koin/navigation graph, and mark isolation complete before allowing a new sign-in. A failure or process death **after the marker** leaves `CleanupRequired`; startup resumes/finishes cleanup for the departing UID before any account graph is created. PR 1 does not offer synchronize, account switch with pending work, destructive discard, or an offline grant.
- **Current PR 1 implementation:** The clean-only sequence now uses a durable UID/epoch marker, a protected account-work registry, SDK write drain, native Auth/Firestore teardown, local cleanup and callback fencing. It permits sign-out only when the initialized registry proves no journal, upload, recovery or offline-grant payload is present. Missing or unreadable registry state blocks departure; post-marker failure enters `CleanupRequired` until recovery succeeds. Android API 34 and a signed iOS simulator proved clean departure, blocked preflight, cleanup failure, each interrupted durable phase, late callback fencing and account A → B isolation with the real adapters; [the PR 1 report](milestone-4-pr1-report.md) records exact runs and remaining release limits. An installation from the earlier PR 1 draft with only a UID pin and no registry record remains fail-closed until an explicit migration or local test reset is reviewed. `clearPersistence` remains SDK cleanup, not secure erasure.
- **States and gate:** Loading retains no protected content; server success enters the verified holding state or WorkspaceGate; invalid credentials, no account, unverified/no member, identity unsupported, account disabled/revoked, offline without grant, timeout, and retry have distinct outcomes. `CACHE` and pending writes cannot satisfy online authorization. Test Auth refresh failure, forged role/tenant records, Rules get/list denials and listener revocation. On **both** Android device/emulator and signed iOS simulator/native Swift bridge, prove clean sign-out clears account-local Firestore/cache and app-owned state before account B signs in; pending journal/upload or stalled SDK write blocks sign-out without Auth change; wait/terminate/clear/local-cleanup failures lock `CleanupRequired`; process death resumes the marker; a late UID/epoch callback and retired SDK generation cannot mutate or expose B. Include cold launch and background/foreground checks. **Acceptance:** no protected role root without a fresh server proof and no fake login/role control; the sign-out control is exposed only after both native isolation/cleanup suites pass and is allowed at runtime only after clean preflight. **Next:** operator-only trainer provisioning and real workspace creation.

## 5. Compact threat and privacy review checklist

- [ ] No caller-provided UID, role, workspace, email, path or cached claim can self-create authority; reject malformed path segments before Firestore references. Test exact identity tuples and supported schemas.
- [ ] Invitation token is random, hashed at rest, rate-limited, short-lived, rotated, single-use and absent from logs, analytics, navigation state, crash reports and trainer-readable summaries. Preview/error responses avoid account enumeration.
- [ ] Fresh verified email and account binding are checked by the trusted accept command. Provider linking and account switching cannot transfer a token to another UID.
- [ ] Every Admin SDK entry repeats authorization. Every client Rules `get` and `list` denies cross-tenant, revoked, disabled and malformed records; client writes cannot change roles, counters, receipts or onboarding completion without the named trusted protocol.
- [ ] Membership caps and catalog entitlement change in the same bounded transaction. Concurrent create/accept/revoke and lost-response replay cannot double-count or resurrect access.
- [ ] Onboarded data is minimum approved data; health/injury fields and analytics content remain absent. Decide purpose, access, retention, consent/age/jurisdiction and export/deletion before expanding.
- [ ] No Milestone 4 offline grant is issued. A future grant is local eligibility only and requires approved duration, download completeness and clock checks; it cannot hide a known revocation. Locked unsynchronized data never appears under another UID; cleanup failure blocks switching.

## 7. Migration and rollback

- **Local/emulator:** Start from an empty named demo project and deterministic seeded fixtures. Do not import production identities or deploy resources. Replace the temporary Foundation root only when PR 1's real authorization gate works; keep its debug catalog isolated. Every new Rules grant is paired with a denial test before enabling a UI route.
- **Existing data before production:** Inventory Auth UIDs against the chosen single-segment contract; unsupported UID means fail-closed remediation, not truncated path construction. Audit account/entitlement schema versions, owner/membership identity, active roster and contribution counters, cap fit and receipt collisions. Backfill missing counters and repair damaged records with a reviewed, idempotent trusted tool while access stays denied. Dry-run Rules/index changes against a copy, then switch traffic only after invariant checks pass. No historical data is silently normalized or erased.
- **Rollout/rollback:** Stage Functions, Rules, indexes and clients in compatible order; keep old clients default-denied on new privileged paths. Preserve receipt and revocation tombstones beyond retry lifetime. If a rollout fails, disable new provisioning/invite endpoints and keep denial Rules/lifecycle tombstones; do not revert to a Rules version that reopens revoked data or restore an older active account/workspace snapshot over a later denial. Roll back UI entry only after pending commands reconcile. External sent links may need explicit invalidation/rotation. Product retention policy governs later cleanup.
