## Canonical scope and inspected baseline

[Roadmap Milestone 7](../implementation-plan.md#7-program-assignment) is **Program assignment**. A trainer assigns an exact published version and the client sees planned workouts whose content does not change with later template edits. The selected architecture is a complete client-safe account-owned immutable snapshot with atomic header, planning, inventory, discovery and receipt. Full lifecycle/expiry/replacement and bounded source/horizon work belong to M7. Active execution/set logging and offline workout recovery belong to M8, review/progress to M9, appointments to M10 and messaging to M11. An assignment's workout date is distinct from an appointment booking.

The [M6 closeout](milestone-6-closeout.md) verifies PR #19 merged and records the disabled committed Publish flag, retained independent native evidence and open acceptance. This plan does not require accepting all of M6 before independent bounded work. It does require selecting a valid immutable version and proving the new end-to-end contract.

## Recommended first end-to-end slice

Recommend **online synthetic create-and-view assignment**, from one currently authorized trainer author to one currently assigned, onboarded client in the same original workspace. Use one verified published version containing **exactly one workout and 1–12 items**, copy that entire version's client-safe content, and create **one planned occurrence**. The client opens its own planned-workout detail and reads the exact copied instructions and prescriptions. The trainer can see the committed assignment through bounded current-relationship discovery. No workout start/log/completion is part of this outcome.

The one-workout restriction is a proposed first-slice reduction, not a change to M6 publication. Reject a larger version with clear unsupported-scope guidance rather than copying only one workout and calling the assignment complete. Supporting all three M6 workouts, each with one occurrence, is the smallest alternative if the owner rejects that reduction, and needs its own measured bounds and confirmation.

**Enabling Publish is not a prerequisite to this bounded slice.** Separately authorized, create-only synthetic fixtures can supply exact published versions that pass the real M6 schema/hash validators. Use an intact original dataset or a distinct newly authorized dataset, with provenance and verified pre-command export. Do not reuse the quarantined dataset. Direct seeding is fixture setup, never evidence of the trainer's Publish journey. If product acceptance requires create draft → Publish → Assign without fixtures, M6 enablement and final-host publication interaction become prerequisites to that larger journey. No flag change is proposed here.

The initial assignment form starts from a current assigned-client detail and an explicit version selection. Preparation returns a client-safe preview, version number/hash, target, schedule, expiry and authority binding. Explicit confirmation freezes all of these. Cancel/Back before submission has no effect. After durable preparation, leaving only cancels presentation. Unknown outcomes stay in the original protected slot. After validated durable settlement, fresh authorized reads show the committed assignment. Client discovery is through its own account/workspace header collection and known assignment's planned-workout paths, never trainer sources or a collection group.

## Authority and immutable source selection

The proposed mediator derives the caller UID from freshly revoked-token-checked, verified, enabled, non-anonymous Auth, with current global account/email binding. Use the existing five trainer authority documents in one transaction: caller account, original workspace, exact trainer membership, own trainer profile and own membershipRef. Validate supported schemas, path identities, active states, contribution flags and positive bounded revisions. Additionally read the client's active global account, exact active client membership, minimal client profile assigned to that caller, membershipRef and valid completed onboarding. Target Auth must independently satisfy the approved eligibility in D2. Auth-service checks cannot be atomic with a Firestore commit, so retain that cross-service limitation and recheck subsequent access.

Capture caller/subject lifecycle revisions, both membership revisions, workspace `membershipRevision`, onboarding revision and current profile-to-trainer relationship in preparation. Execution compares the exact tuple transactionally. A future relationship writer must advance the relevant membership revision; raw Admin edits are outside the contract. Authority loss denies business reads/writes/replay without manufacturing a terminal conflict. Original eligible global identity may still obtain its minimal own outcome. Independently restored authority cannot rebind the submitted tuple.

Select **`workspaceId + templateId + versionId + versionNumber + sourceContentHash`** and the assignment-copy policy version. Validate the version's exact stored schema, original owner/workspace/path, canonical content hash and completeness. Read the exact version inside the transaction and derive copied content there. Root reads may establish identity/integrity but must not require that selected version is still current or that today's mutable draft revision is unchanged. Publishing v2 or saving a new draft after selecting v1 must still assign v1. No execution-time “latest,” mutable draft, client-supplied workouts, asserted copy hash or lazy exercise lookup can replace the confirmed copy.

Recommend assigning from the retained immutable version without live exercise/source revalidation: publication already copied those definitions, and authorized version reads do not require current source entitlement. This is a D2/D3 policy recommendation requiring approval. Correcting/withdrawing an exercise later must not refresh assignment text. Removing template-author authority denies a new assignment. Once copied, client access is evaluated on the assignment's own gate and approved relationship/lifecycle policy, not by granting source reads.

## Atomic materialization and client reads

Use the selected account-owned layout and the complete copy before activation. Generate stable assignment/plan IDs once before the retryable callback and retain them in the protected descriptor. Proposed write set for the first slice:

1. `users/{clientUid}/workspaces/{wid}/assignedPrograms/{aid}` — safe identity/provenance, trainer, snapshot hash, revision 1, ready/active, confirmed scheduling/expiry metadata. No instructions or private fields in the listable header.
2. `.../{aid}/snapshots/content` — immutable client-safe title/description/provenance/hash and bounded structure information, with one workout and all its exercise child documents containing the complete approved copied text and typed prescriptions.
3. `.../{aid}/plannedWorkouts/{pid}` — exactly one plan pointing to that copied workout, confirmed instant, status planned, revision 1. No dangling plan references.
4. `.../{aid}/manifests/download` — sorted duplicate-free inventory of the snapshot, every workout/item and plan path, identity/schema/hash/revision. It remains a server inventory even though PR 1 is online-only.
5. `workspaces/{wid}/assignedPrograms/{aid}` — minimal trainer discovery index. No independent authorization or private content. No separate workspace planned-workout index is required for the first known-client discovery flow.
6. Shared workspace `membershipRevision` advancement and the immutable `lifecycleCommands/{commandId}` decision, in the **same business transaction** as every artifact above.

All target/index paths must be unused. Read complete authority, command history/config, exact version and required integrity records before any writes. All-or-none commit includes header, every copy/plan/inventory/index, workspace fence and receipt. No delayed child fan-out, partial-ready state or notification-driven activation. Aborted/oversize creation changes none of them. Admission rate counters are separate bounded metadata and may commit on a rejected attempt.

Client reads use fresh official SDK server reads in the existing product memory-cache configuration. Current Rules require authenticated verified own UID, active schema-current account/workspace/client membership and exact header identity. Content adds ready/active, fixed snapshot `content`, valid `accessExpiresAt > request.time` and path-matching tuples. Four distinct direct authority documents gate each descendant. Header list authorization relies on trusted-only path-correct safe writers; unknown/private fields cannot be made safe by a client parser. Require strict whole-document validation/admission before publishing them.

Use exact UID/workspace bounded header queries and identity-constrained children/plans under one assignment, with explicit page limits/lookahead and complete validation including lookahead. No cross-assignment collection-group query. Validate the entire copied set and recomputed snapshot hash, then re-read header revision/eligibility after multi-read loading. Changed/denied/incomplete reads clear or reject the detail, never render a successful partial workout. Measure actual Rules access calls for each query/batch, without assuming caching reduces them. No cache-only success or local durable download manifest is introduced.

Client direct source root/version/all-descendant get/list/write stays denied, including the exact assigned version and custom sources. Inventory paths must be validated relative descendants under the same UID/workspace/assignment; never follow arbitrary source/private paths. Required exercise text is inside the copy. Trainer source ownership and copied content provenance grant the client no additional document access.

## Publication and assignment size feasibility

M6 source publication permits 1–3 complete workouts/12 items, 650 combined draft scalars plus up to 2,000 instruction scalars and bounded taxonomy per item. Immutable version validation is 160 KiB, publication preview/version-get packets alone 192 KiB. Those limits do not authorize a 192 KiB assignment mutation, proof, aggregate list or new client read. The assignment primitive's supplied string prescription is incompatible with the current exact integer/null prescription without a deliberate mapper/schema contract.

Recommend retaining bounded assignment children, with one item per document and narrow client DTOs. Proposed first-slice ceilings to prove are snapshot header 8 KiB, workout/plan/header/index/receipt each 4 KiB where applicable, item document/result 24 KiB, inventory 8 KiB and every complete bridge packet at most the existing generic 64 KiB. Fetch items separately or in explicitly byte-bounded pages, not all twelve full instructions in one generic response. Source-version reading on the server may use the M6 160 KiB validation ceiling. None of these proposed assignment caps has been measured or approved by this plan.

The existing layout's business write formula is **`6 + W + I + P`**: assignment header, snapshot header, manifest, trainer index, receipt and workspace revision, plus workout/item/plan documents. For W=1, I≤12, P=1 this is **≤20 business writes**, plus a proposed one-write admission counter. Reading the source/root, global/relationship authority, coverage, both receipt namespaces and collision guards also needs an exact finite read budget. The primitive's caller-supplied `maxWrites` is not product admission. Trusted configuration must own all caps, count all documents, enforce at most three transaction attempts and bounded elapsed checks/rate admission. Five-second application checks do not cancel an in-flight SDK RPC.

Before issuance, implement real TypeScript/Kotlin canonical serialization and hash vectors for the small descriptor binding target, source version/hash, copy-policy/hash, IDs, authority, schedule and expiry. The server must rederive the same copy and hash; a hash alone never authorizes a caller-supplied copy. Measure actual Admin SDK document/commit protobufs including paths/transaction metadata, index count/bytes and complete responses. Derive deterministic bounds for all legal Unicode/escape/ID/numeric boundaries, not just representative content. No new universal Firestore/SDK limit is asserted from historical M6 measurements.

Keep requests ≤32 KiB, resolver ≤8,192 UTF-16 units and 24,576 UTF-8 bytes, pending ≤16 KiB and existing generic plaintext/encrypted budgets 64/96 KiB. Recommend the proven **36,500-byte prospective new-kind ceiling** only if the actual new descriptor/proof forms fit it with every retained history class and maximum departure marker. Serialize the actual prior envelope and every preparation/resolving/normal/conflict/resolver/full-proof/retired/departure state under the native lock. Use deterministic unchanged Swift/Android wrapper bounds and actual native output. Oversize must reject before durable preparation/issuance with existing encrypted bytes identical. Historical custom admission stays a separate finding. If a bound fails, disable Assign and report the exact state and smallest content/shape alternative; no generic cap increase, truncation, second store or clearing old proof.

## Recovery namespace reconciliation

The security design names `lifecycleCommands`, but both isolated `publishAssignment` and `closeAssignment` currently write **`assignmentCommands/{commandId(callerUid,key)}`** and hash their primitive inputs, including supplied content/config. They lack covered-generation checking, the twelve-kind resolver adapter, native persist-before-send, whole-key lifecycle fences and ADR-002 retirement. An absent lifecycle receipt says nothing about a possible legacy assignment receipt. Two independently consumed namespaces cannot provide the current whole-key guarantee.

Recommend new product assignment creation use `lifecycleCommands`, a proposed **`program-assignment-create` / `program-assignment-v1`** adapter, and the existing one-command encrypted UID slot. Names and exact descriptor/result/conflict fields must be frozen under D8 before coding. Preserve all twelve original variants/hashes/forms and full legacy proofs. Do not rename or migrate historical `assignmentCommands` records into fabricated current proofs.

Namespace work must precede coverage/issuance:

- Inventory both legacy writers, tests and all entry points. Keep primitive close/replacement unexposed. Reject covered product keys at legacy assignment writers, or make every such writer participate transactionally in the same whole-key guard before permitting them. Merely removing an export is insufficient proof.
- For a product caller/key, check retained `assignmentCommands` identity alongside `lifecycleCommands` before creating an effect or absence fence. Occupied, mismatched, unsupported or dual records fail closed pending separately reviewed compatibility. No cross-namespace replay by guessing hash equivalence.
- Extend the own resolver with exact new-descriptor/receipt validation and original-global-identity permission. No live client/workspace/source lookup is required to disclose the seven content-free outcome fields. Preserve finite budgets, intact provenance/generation checks and missing-history locks. Do not claim new assignment history is covered simply because other commands already use that generation.
- Prove legacy writer versus new fence, new writer versus resolver and cross-kind/key collisions with transaction barriers. Historical records/config/consumed keys stay intact. Never create new history or rekey unresolved work to establish absence.
- Normal applied/conflict acknowledgment must bind the original command and minimal decision. Generic Auth/service/expiry/validation errors never settle it. D8 must specify durable stale-preparation/schedule/hash conflicts precisely, including which current authority permits their receipt. Full proof must be durably written before content-free retirement. No target, workspace, schedule, source version/content or raw key remains in the proposed marker.

Business exact replay rechecks current business authority and returns the original decision, even after a later source version exists. Own-resolution can settle after workspace/relationship loss when the original global identity is still eligible, without reopening content. The result means that command applied historically, not that the assignment remains active. Fresh client/trainer reads establish current visibility. Disabled/deleted identity, corrupt storage and unproved history remain locks.

## Trainer index limitation and revocation/history

Current trainer index Rules require only the requesting trainer's active account/workspace/membership and the index's schema/path/trainer identity. They do not check the indexed client's current membership, account or profile relationship, nor join the assignment's expiry. A still-eligible trainer may read retained metadata after client loss. Existing M5 revocation therefore rejects every retained header/index, including expired/terminal artifacts, and source M6 work avoided the index entirely.

The proposed first slice introduces those artifacts. Its default **A prerequisite** is D7 plus a narrow Rules/discovery correction, reviewed in a later authorized PR. Recommend deny direct trainer index reads and use current-relationship mediation; prove actual denied SDK get/list as well as mediator checks. A constrained trainer query alone cannot fix stale access. A point-read-only alternative would need exact client/relationship/parent predicates and separately proved list behavior/access-call bounds. Do not promise that per-row Rules joins make an unconstrained list authorizable.

This correction does not automatically enable membership revocation for assignment-bearing clients, add a historical trainer grant or delete artifacts. Keep the artifact guard until an approved later policy specifies denial, safe metadata/history, workspace fencing and cleanup. An owner could separately approve a synthetic-only deferral of the discovery limitation with explicit metadata exposure and no client-withdrawal/history scenario, but this plan recommends the correction and records no such waiver. Hiding the trainer screen would leave direct Rules access present.
