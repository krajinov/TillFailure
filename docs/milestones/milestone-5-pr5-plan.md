## Recommended initial scope

Recommend a **synthetic-data, emulator-only** first slice: one plain-text note for one client/workspace, owned by the individual authoring trainer and usable only while that same trainer remains assigned and both parties remain eligible. Read, create and explicitly save corrections; no collection listing, timeline, search, autosave or collaboration. One deterministic slot deliberately prevents a second author taking over an old note. It is a product access identity, not a determination of legal data ownership/controller status.

Exclude health/injury/diagnosis/disability, medication, mental-health, biometric or other sensitive information; contact/financial/credential/third-party personal information; attachments, photos, tags, pinning, history, shared notes, client feedback, export, deletion/archive, transfers and former-client records. Proposed permitted purpose is non-sensitive coaching administration, such as “Review exercise demonstration next meeting.” Even innocuous free text can identify a person: no real personal data or assumption that helper text can classify/prevent all sensitive input. Show a concise purpose/exclusion notice; no automated sensitive-data classifier or new dependency. Real-data use needs separate privacy/content approval.

### Proposed access decision table

All business operations require fresh enabled verified non-anonymous caller Auth, active schema-current global accounts, active workspace, exact active path-bound memberships, supported identity/revisions and current clientProfiles.trainerId. Author also needs their exact trainer profile; both parties need their exact active discovery references. Check that the subject's Auth account still exists and is enabled without requiring a subject token. Onboarding may be pending or complete, matching the existing assigned-client detail scope. Identity supplied in the request never determines the author.

| Actor or event | Read / create / correct | Lifecycle result proposed |
|---|---|---|
| Author who is still the assigned active trainer | Yes, exact slot only, with every gate above and stored relationship bindings unchanged | Author is immutable Auth UID; no workspace ownership prerequisite for notes. |
| Assigned trainer who is not the stored author | No read or correction; no replacement of an occupied slot | Assignment does not transfer a previous author's note. No reassignment feature in this slice. |
| Workspace owner | Only when also the eligible author/assigned trainer | Ownership alone gives no override, export or support role. PR 4 removal still separately requires owner AND assignment. |
| Other trainer, including same workspace | No | No existence/count/preview/list disclosure. |
| Subject client or any other client | No through any product API, direct Rules path, query or derived projection | “Private” is server-enforced exclusion, not merely hidden UI. No note content or existence in client-facing DTOs. |
| Author/subject membership revoked, assignment changed, workspace suspended | No new business read/write; retire presentation on known loss | Preserve latest record under inaccessible custody, not historical author access. Revocation must remain possible. |
| Author or subject global account disabled/deleted/missing, or either Auth account disabled/deleted | No business access; no identity repair | Retained records do not grant access. Own-command resolution remains possible only for an eligible original initiating global identity. |
| Restoration/rejoin/return to prior trainer | No automatic historical access | Revision-bound records fail closed after relationship/lifecycle changes; no rebinding/migration is in scope. |
| Support/operator | No product support endpoint, impersonation or general receipt/note browser | Admin/IAM can technically bypass Rules; least privilege, audit and any support access process require separate approval. Do not promise end-to-end encryption or secrecy from infrastructure administrators. |

No ownership or access transfer is supported. Unknown/malformed authority denies. Current membership alone is insufficient for a retained record: bind its original author/subject membership and global lifecycle revisions as described below. This conservative first scope also seals old notes after workspace suspension/restoration changes membership revisions, or disable/enable changes global lifecycle revisions. It intentionally provides no automatic restoration policy. Unrelated profile edits and workspace roster changes do not invalidate those stored bindings.

### Retention, revocation custody and deletion boundary

**New proposal requiring explicit approval:** retain the latest note in place when access is withdrawn, with immutable author/subject/workspace and original relationship bindings, behind denied business access. Existing retained membership/profile records anchor custody; the backend data custodian remains responsible for these inaccessible records. This is an explicit retained-record state derived from authority/binding checks, not an abandoned orphan, a right to view former-client records, or a newly granted owner role. No note-derived field is added to client-readable parents.

For the proposed local synthetic slice, retain fixture records and command barriers with their dataset attribution, as existing recovery tests require. This does **not** select a real-data retention period or approve indefinite retention. Before real-data use, product/privacy/operations must decide active-note retention, disposition after each revocation/reassignment/suspension/account-deletion event, export/discovery obligations, backup copies and operational custody. If inaccessible retention is rejected even for the first slice, revise this design before implementation; do not silently delete notes or block revocation to avoid that decision.

No Delete, Clear, Archive, automatic TTL or purge command is included. Corrections replace current text with nonempty text and advance revision; there is no server note-version collection. Correction is not a guarantee that old bytes vanish from pending device work, backups or infrastructure storage. Account disable/deletion denies access first; this plan does not implement account deletion or claim it erases notes. A future purge must serialize with writers, prevent recreate/replay, preserve consumed-key barriers, account for offline pending envelopes and backups, and have separately approved semantics/timing. A client has no product note API; that does not decide legal discovery/export rights.

Use existing immutable command receipts for minimal mutation accountability (actor, binding, outcome, time); no note text, previous value or free-text audit reason. No new audit/history product or read-access audit is claimed. Retention of identifiers and fingerprints is also a policy question. No receipt/fence expiry while a key remains executable; future compaction requires permanent key retirement across all writers. Support/export/discard of locked local text is excluded and remains a decision, not a promised recovery option.

## Proposed document and operation contract

### Exact paths and payloads

One slot: `workspaces/{wid}/privateTrainerNotes/{clientUid}`. The document ID is the subject UID, using the repository's representable single-segment UID contract; author is derived from verified Auth. Fixed slot means at most one note per client/workspace, including after revocation. No random note collection IDs, descendants, collection-group queries, lists, cursors, composite indexes or arbitrary path selectors. Hashing UIDs is not used to bypass existing UID compatibility policy.

Proposed exact stored allowlist:

| Fields | Contract |
|---|---|
| `schemaVersion`, `policyVersion` | Integer 1 each. Unknown/missing versions fail closed; no implicit migration. |
| `workspaceId`, `subjectClientId`, `authorTrainerId` | Immutable, exact path/verified caller bindings; author must equal current assignment. |
| `authorMembershipRevision`, `subjectMembershipRevision`, `authorLifecycleRevision`, `subjectLifecycleRevision` | Immutable creation-time values, integers 1..2147483646; equality to current authority required for subsequent business access. No update can rebind a closed record. |
| `body` | Nonempty after checking whitespace, at most 2,000 Unicode scalar values and 8,000 UTF-8 bytes. Reject unpaired surrogates, NUL and control characters other than LF/tab. Normalize CRLF/CR to LF once before durable preparation; no other trimming or Unicode normalization. Server validates canonical form and rejects rather than transforms. |
| `revision` | 1 on create, then exactly prior + 1; maximum 2147483646, writes reject exhausted revision. |
| `createdAt`, `updatedAt` | Server Firestore Timestamp; creation time immutable, update time set in the commit transaction; never client clock or ordering/concurrency authority. |

No separate title, visibility flag, raw command key, last body, search terms, subject name/email, createdBy/updatedBy duplicates or archive fields. The immutable author supplies actor identity for this single-writer policy; this narrower proposal deliberately specializes the broad schema audit-field convention. Timestamp projections use bounded epoch milliseconds and explicit types.

Proposed guarded `trainerNotesEmulator` mediator has only two actions:

- Read: `{action:"note-get", workspaceId, clientUid}`. Under fresh authorization return `{status:"note", workspaceId, clientUid, note:null|{body, revision, createdAtMillis, updatedAtMillis}, authority:{authorMembershipRevision,subjectMembershipRevision,authorLifecycleRevision,subjectLifecycleRevision}}`. Null means authorized empty slot. Ineligible/closed/malformed slots use redacted denial/unavailable categories, not existence disclosures. No note content in the roster/details DTO.
- Save: `{action:"save-trainer-note", workspaceId, idempotencyKey, noteSave:{clientUid,body,bindingNonce,expectedRevision,authorMembershipRevision,subjectMembershipRevision,authorLifecycleRevision,subjectLifecycleRevision}}`. `expectedRevision=0` means create at an absent slot; otherwise requires existing exact revision. A slot occupied by another author or relationship is never an authorized create/conflict preview. `bindingNonce` is fresh 32 cryptographically random bytes encoded as 64 lowercase hex, created once before preparation and retained unchanged with the command. Reject extra keys, wrong numeric types and missing fields at every boundary.

Canonical kind `trainer-note-save`, request hash format `trainer-note-v1`, policyVersion 1. Proposed `requestHash = stableHash({...exactSaveRequest, callerUid:verifiedUid, policyVersion:1})`, using existing canonical hashing with cross-language vectors. Nonce makes a retained hash less useful for guessing short text, but the hash is a binding, **not encryption/anonymization**. Never persist the nonce or text in a server receipt/fence. The nonce remains in the pending descriptor/proof and transient request only; committed text belongs in the protected note document. Existing command keys remain `or1-{supportedGeneration}-{nonce}`; that key nonce and content bindingNonce are distinct. Do not change hashes/formats of the existing seven actions.

### Fresh authorization, work bounds and concurrency

Use the current named-demo/loopback export guards, fresh bearer verification including revoked-token checks and enabled verified Admin Auth lookup. Add one bounded Admin Auth lookup for the subject's existence/enabled state; it supplies no subject identity/contact fields to the response. Every request and business replay transaction reloads author account/email/lifecycle, workspace, exact author membership/profile/directory, subject account/lifecycle, subject membership/profile/directory and slot. A trusted account-deletion workflow must deny the Firestore account before external Auth deletion. External Admin Auth changes are not atomic with Firestore: document and test that limitation rather than claim instant recall of a response already authorized. An Auth-only disable/enable cycle without a corresponding global lifecycle revision is not a supported restore path and cannot establish the historical-binding guarantee. Already returned text cannot be remotely erased.

Read the ten fixed business documents above (including the slot), plus command receipt and coverage configuration for Save: **at most 12 fixed documents, no query/fan-out** per attempt. Validate the existing authority shapes; target account reads need no name/contact fields. Set an exact application request/response ceiling of 32 KiB serialized UTF-8, including JSON escaping, IDs and envelope; reject oversize before path construction. Note body has the tighter limits above. Three transaction attempts and the existing five-second elapsed-work check before writes; this is not RPC cancellation. Cap stored note payload to 16 KiB and bound source reads by Firestore document limits; enforce measured budgets in tests. Add a payload-free per-caller request counter at `trainerNoteRequests/{stableHash(uid)}`, exact `{minute,count}`, fixture cap 120/minute, one read/one write in a separate admission transaction (including failures/replays). This is a proposed emulator engineering bound, not production rate policy. Existing resolver limits and finite fence budgets remain separate and unchanged.

All business reads occur before writes. Successful Save writes exactly the note and immutable receipt, atomically. A recognized stale note revision under still-valid identical authority records only a conflict receipt (one write). Future expected revisions, corrupted sources, mismatched owner/bindings or lost authority produce no terminal business receipt and no note write. Transaction contention reruns fresh checks. Never turn a generic permission/precondition/network failure into a durable conflict.

Two devices saving revision N: one commits N+1; the other commits a bound conflict with observed revision greater than N. Missing slot at expectedRevision>0 is inconsistent, not permission to recreate. Same key with changed text/nonce/target/revision/kind cannot execute. No last-write-wins, silent overwrite, merge or automatic retry with newer revision. Conflict UI preserves the losing draft only in the current authorized foreground editor; explicit fresh reload is required, with confirmation before replacing a dirty draft and replacement only after read succeeds. The user can then compose a correction against the new baseline with a **new** key. No persistent conflicting-copy history.

### Receipts, resolution and protocol choice

Reuse `lifecycleCommands/{commandId(verifiedUid,idempotencyKey)}` and its whole-key consumption invariant. Proposed receipt exact allowlist: `{schemaVersion:1,commandKind:"trainer-note-save",callerUid,workspaceId,clientUid,requestHash,result,committedAt}`. Exact result: `{status:"note-saved"|"note-conflict",workspaceId,clientUid,noteRevision}`. Saved revision equals expected+1; conflict revision is strictly greater than expected. No text, nonce, prior value or receipt reconstruction from the current note. Normal response adds only `replayed` to that result. Bind the normal acknowledgment to its captured original command under native ownership; do not fabricate a server hash/time echo.

Assessment of alternatives:

1. Direct Rules CRUD plus lastOperationId would need new Rules and a proved native ordinary-write/rejection protocol; a later edit can replace lastOperationId, and authority loss prevents inspecting the note to settle earlier work. A generic mutationJournal entry does not already solve this. It also risks SDK persistence of note bodies. Not recommended for this first slice.
2. A process-only online write avoids local text but cannot preserve the exact original binding across process loss or reliably unblock clean departure after an ambiguous response. Not recommended under the requested recovery contract.
3. **Recommended:** one new typed Save descriptor/receipt adapter in the existing protected slot and resolver. Read is not a protected variant. This is a narrow eighth action, not a new ledger, queue, resolver, database or generic framework. Its necessity follows from durable Save/restart/authority-loss requirements, not CRUD alone. If local submitted-text persistence is rejected, revise those requirements before selecting another design.

Own-command resolution sends the exact protected original descriptor (including original text/nonce for hash recomputation) over the existing transport; the server validates it transiently and never writes/logs it. It returns the existing exact seven-field outcome projection. No note read, subject/account lookup or workspace authority is required for the resolution decision. Add strict positive/conflict/fence adapters and register the writer under existing generation/provenance coverage before enabling issuance. Every existing receipt/fence/unsupported record consumes the entire caller/key. An absent receipt alone is never a negative outcome. Resolver-first prevents delayed Save; Save-first projects the original result without returning current text. `applied` means the original Save committed, even if the note was later corrected or access withdrawn.

The current resolver additionally rejects serialized requests above 8,192 UTF-16 code units (`JSON.stringify(raw).length`). Before pending admission, prove that the complete resolution wrapper for every accepted Save fits that existing limit as well as the proposed byte cap, including maximum escaped IDs/body; enforce the same validation on the server. Do not admit a Save that cannot subsequently resolve, or globally raise limits for existing variants without review. Freeze UTF-8, scalar-count, JSON escaping and canonical-hash boundary vectors across TypeScript/Kotlin/native bridges.

### PR 4 interaction and atomic ordering

Retained notes **do not enter** PR 4's assignment-artifact probes, do not add owner permissions, do not require reading note content, and do not block removal. The recommended custody policy needs no note scan, note write, extra revocation revision or change to its five-write success transaction. A locally pending Save still occupies the existing single slot, so that installation must Retry/Resolve before issuing revocation; another eligible installation can revoke immediately. This is a device recovery constraint, not server denial of revocation because a note exists.

The required serialization is the Save transaction's **reads of the exact authority documents changed by revocation/lifecycle**. PR 4 updates subject membership and workspace atomically. Save-first may commit and then become inaccessible when revocation commits. Revocation-first forces a competing Save to retry/deny; a note cannot commit against a previously read active membership after revocation. No empty collection probe is used as a lock, so the extra workspace revision write required for assignment publication is unnecessary for this fixed-slot design. Do not increment workspace membershipRevision on every note edit or make unrelated roster changes stale the editor.

Reassignment must atomically change clientProfiles.trainerId and advance the subject relationship revision; Save reads both. It is not implemented here. Current catalog suspension changes workspace status and membership revisions; account lifecycle changes account status/revision. Those are in the Save read set and stored binding checks. No future restore may silently rebind an old note. Any later policy choosing atomic text deletion or transfer at revocation would require a separately reviewed bounded lifecycle transaction and receipt version/compatibility review; a background cleanup trigger cannot establish that atomic policy. Existing assignment-index Rules limitations and the assignment-bearing removal guard remain unchanged.

## Native recovery, local content and editor lifecycle

Unsent drafts and freshly read note bodies are memory-only. No SavedStateHandle/rememberSaveable text, navigation payload, preferences, Firestore cache, local note table, clipboard export action, analytics/crash breadcrumb, notification preview or fixture-log body. Mediated reads avoid sending note documents through the mobile Firestore cache. Audit both native transports and diagnostic paths; “online only” alone is not storage proof. OS keyboards, app-switcher capture and device compromise are separate protection concerns; verify lifecycle blanking and keep physical/security acceptance open.

**Submitted text is persisted locally** only as the single original pending Save command and its pending terminal proof in the existing authenticated encrypted UID envelope. Android location: `Context.noBackupFilesDir/tillfailure-recovery/account-{SHA256(uid)}-v1.json`, AES-256-GCM via Android Keystore, UID in authenticated data. Apple location: Application Support `TillFailureRecovery/account-{SHA256(uid)}-v1.json`, CryptoKit AES-GCM, Keychain key `tillfailure.recovery.v1` with `AfterFirstUnlockThisDeviceOnly`, file `completeUntilFirstUserAuthentication` and backup exclusion. These are existing protections, not a claim of secure erase, hardware backing or protection while an already-unlocked device is shared. Pending work can remain indefinitely when identity/storage cannot recover; no expiry/discard is authorized. This retention exception needs explicit approval.

Native admission persists the canonical body/key/nonce/revisions before token issuance/transport, under the existing freeze/UID lock. A failed/ambiguous preparation cannot send or replace the slot. Retry uses the exact original payload and current business authority. Confirmed Resolve durably marks resolutionStarted and stops new ordinary retries; server fences cover already in-flight requests. Cancellation retires presentation only, not potentially committed work. Native settlement continues after editor disposal under original UID/generation; display/navigation additionally require current workspace/role/authority epoch and editor visit.

**Required proof-compaction prerequisite:** preserve the first atomic write of original pending command plus fully validated terminal proof. In the second atomic write, validate that exact binding again, retire pending work and replace it with one versioned **content-free last-settled marker** for note commands. Proposed marker allowlist: `{schemaVersion:1,uid,commandKind,commandId,requestHashVersion,requestHash,source,outcome,decidedAtMillis?}`; time exists only for a validated resolver source, never synthesized for normal acknowledgment. It contains no original command, text, nonce, client/workspace ID or raw key. Compute duplicate-key refusal from uid/key→commandId. Restart validates the authenticated envelope and marker shape; it must not pretend to recompute a discarded body's hash. Only the prior validated proof-to-marker transition establishes settlement. Do not accept arbitrary unbound network replies as markers.

Keep the same bounded last-proof slot, with an explicitly tagged compatible schema for legacy full proofs versus new note markers; update all admission, memory-consumption, presentation and restart consumers. Do not simply drop fields from CommandTerminalProof, whose current validation requires them. Old supported records remain valid; unsupported older clients must lock rather than erase/replace new work. Test upgrades/downgrades and wrong markers. A failure before proof leaves unknown work; after proof leaves restart-retirable work; after compaction cannot reissue. Clear pending/proof/transport text references after settlement; an authorized foreground conflict draft follows the explicit reload/exit policy above. Scope retirement clears all presentation text. Do not promise byte-level memory or disk secure erasure. Record the accepted schema/architecture decision before code if this proposal is approved.

No access-loss callback may restore a retired editor; no recovery proof opens a shell. Preserve PR 4's stable owner-scoped NavigationStores defaults and saved-state decorator ordering. The editor uses immutable MVI State/Event/Effect, Route/Screen separation, project-owned DTOs and a destination-owned ViewModel; native hosts stay thin. Reuse the root-owned command/recovery service, not a second feature ledger.

The existing identity observer covers caller/root authority; it is not proof of immediate notification when the subject is revoked or reassigned elsewhere. With direct note/foreign-membership reads denied, this initial proposal adds no target listener or polling grant. Revalidate through note-get on entry, foreground/reconnect and explicit reload, and through fresh authorization on Save. Known denial clears text immediately; remote changes unknown to a foreground editor may remain visible until that next check. Instant target-change invalidation would require a separately designed authorized notification mechanism; do not claim it from shared injected events.
