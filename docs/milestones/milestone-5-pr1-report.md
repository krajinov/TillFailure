## Authority and source boundary

`clientsEmulator` is a dedicated list/get callable guarded by the existing exact demo-project and loopback Auth/Firestore checks. Every call refreshes current Admin Auth eligibility and checks the caller account's schema/status/lifecycle revision/email binding, selected active workspace and exact path-bound active trainer membership. A body UID/trainer/filter cannot select authority. No ownership assumption grants access to another trainer's clients; an adversarial second active trainer test proves this without enabling a multi-trainer product.

Inside one read transaction, target membership supplies relationship eligibility; the exact client profile supplies assignment (`trainerId == caller`), identity, creation time and workspace onboarding state. Only assigned targets proceed to an active/schema-current account/name check. Missing/malformed sources fail closed without a partial response; recognized disabled targets are omitted. Details re-read all current authority and target sources independently of the roster. Previous pages, IDs, saved destinations and cursors grant nothing.

The authoritative name is `users/{clientUid}.displayName` with the existing global basics/revision validation. The recognized revision-zero empty bootstrap is nullable only while workspace onboarding is pending. Partial basics and completed-but-empty names fail closed. Target account field masks exclude email; locale/time zone are read internally only to validate the existing basics shape. Snapshots are never serialized. Explicit named scalar projection prevents additional account/profile contact, health or private-note fields from escaping.

Each item/detail contains exactly `clientId`, `workspaceId`, `displayName`, `relationshipStatus`, `onboardingStatus`. The page adds only `items` and `nextCursor`. No relationship count, skipped count, hidden ID, revision, timestamp, scan position or diagnostic reason is public metadata. Mobile Rules are unchanged: other-user accounts, other-client profiles and membership/profile enumeration stay denied. Reads add no command, receipt, ledger payload, persistent cache or recovery queue.

## Complete-set pagination and budgets

This implements the final merged correction, not the superseded historical-profile scan. Every page queries only the exact workspace memberships collection with `status == active`, document ID ascending, `limit(B+1)`, selecting membership validation fields. B is the existing trusted invitation fixture cap of **5**, including trainers. The complete query result must fit B and agree with the workspace active roster/contribution counters; the aggregate revision is validated and read transactionally with the sources. A counter alone never establishes authority/completeness. Historical revoked memberships and orphan/retained profiles are not enumerated.

Authorized rows are joined and sorted in memory by creation timestamp seconds, nanoseconds and unique client ID. Full SDK timestamp components are retained; emulator timestamp fixtures use microsecond-aligned nanoseconds because Firestore truncates finer stored precision. Names/onboarding do not affect ordering. A page fills from authorized rows only; nextCursor exists only for an additional currently authorized row. The cursor position is the last returned authorized row, never lookahead or a hidden source. Hidden-only suffixes produce no continuation. No anchor lookup, assignment check or existence probe is performed when resuming: the authenticated position is compared against the freshly rebuilt set even if its former row has disappeared.

At B=5 the conservative per-attempt source ceiling is 3 fixed authority reads + 6 membership query documents + 5 profiles + 5 account lookups = **19 documents** (the active trainer reduces actual client joins further). Configuration reserves 20 reads/20 MiB and refuses a cap/read/byte configuration that cannot cover the entire worst case, independent of page size or actual data. The byte proof conservatively reserves Firestore's 1 MiB maximum per source document rather than assuming short fixture values. Scalar validation still rejects oversized projected values. There are at most three transaction attempts: the conservative request ceiling is 57 source documents/57 MiB across those attempts, with a five-second Firestore-work deadline after fresh Auth. No refill loop exists. A service timeout/retry exhaustion/counter drift/cap overflow returns generic unavailable without items or continuation; the UI does not treat that as exhaustion. Underlying SDK cancellation is cooperative; a timed-out read can finish internally but cannot publish a late response.

Page size accepts integer 1–20; the product uses 2 to exercise paging under the unchanged cap. The real Admin query executes in the emulator tests. It uses the default status single-field index/document-name ordering; no client-profile/name composite index or index deployment was added. Emulator success does not establish production index readiness.

## Cursor confidentiality and lifecycle

The trusted worker uses Node crypto AES-256-GCM: canonical bounded state has an internal four-byte length prefix and zero padding to **4,096 plaintext bytes**, a fresh random 96-bit nonce and 128-bit tag. The fixed public header contains only format version 2 and a random 16-byte key ID. The envelope is 4,141 bytes, **5,522 base64url characters**, with a strict 6,144-byte input ceiling and canonical encoding validation. No names/contact/sensitive content enter it.

Encrypted state binds caller/trainer/workspace, fixed assignment filter/purpose/query/order/serialization version, page size, caller membership revision, last returned timestamp/ID tuple and original issuedAt/expiresAt. AAD additionally binds canonical service, environment and project plus server-derived request context. A traversal lasts at most 300 seconds; later pages retain the original expiry. Aggregate workspace revision is not a cursor condition: hidden relationship changes do not invalidate a token. Every page nevertheless reauthorizes and reprojects current sources.

Malformed, oversized, tampered, foreign-scope, wrong-version, unknown/retired-key, future/expired and caller-revision-mismatched cursors all map to the same failed-precondition `invalid-cursor` response requiring reload. Authentication completes before plaintext parsing or target queries. Real callable tests compare exact error bodies. Caller access denial remains its safe gate independent of cursor content. This is response-field confidentiality, not constant-time execution or traversal-wide snapshot consistency.

Random 256-bit keys/key IDs are generated at guarded emulator-worker startup and held only in that process. A discovery/non-emulator process gets no demo key; operations refuse fallback. Rotation occurs at one hour or 2^20 issuances, with fresh nonces, prior decryption only through the last issuance's maximum lifetime, emergency retirement and restart invalidation. Tests exercise clock/issuance boundaries and key retirement. Production still requires a separately approved protected multi-instance key ring, coordinated budget/rotation and rollout configuration; this emulator guard cannot enable it.
