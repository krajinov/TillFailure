## Proposed sequential PRs

### PR 1 — Online named roster and minimal assigned-client details

**User outcome and approved scope:** An active trainer opens Clients, pages through their own assigned active clients by name, and opens minimal relationship/onboarding details in the selected active workspace. Josip approved this narrow read behavior on 2026-10-17. The same workspace does not entitle a trainer to another trainer's clients. Pending-onboarding clients may not yet have a name; show an honest “Name not provided yet” label rather than inventing one or exposing contact information.

**Included/excluded and minimal payload:** Each list item and detail returns exactly `clientId`, `workspaceId`, `displayName` (validated string or `null` for the recognized unnamed bootstrap state), `relationshipStatus=active`, and `onboardingStatus=pending|complete`. IDs are navigation identity, not grants. Revisions and pagination sort values remain confidential authenticated cursor/internal consistency metadata, not plaintext pagination fields or additional client profile fields in the UI. A page envelope adds only `items` and `nextCursor`; no total-client or attention counts. Exclude contact information/email/phone, health, notes, search, profile editing, reassignment, membership/lifecycle actions, photos, joined/since dates and all later-milestone metrics. Existing own-client Profile remains intact.

**Authoritative assignment and status:** `workspaces/{wid}/clientProfiles/{clientUid}.trainerId` is the trusted assignment source, created from the verified inviter by invitation acceptance. It must equal the authenticated caller UID; neither a request's trainerId nor a workspace owner field substitutes for it. Validate profile schema, stored workspace/user IDs against its path and supported onboarding shape/revision. Relationship status comes from the exact path-bound `workspaces/{wid}/memberships/{clientUid}` with client role; onboarding status comes from that workspace profile. Both caller and target accounts must be active/schema-current, the workspace active/schema-current, and both memberships valid at their exact paths. An assigned profile alone never grants access after membership revocation. Reassignment is excluded; any future assignment writer must define authorization and cursor invalidation explicitly.

**Authoritative name and consistency with onboarding:** The sole name source is `users/{clientUid}.displayName`, with its `profileRevision` and recognized bootstrap validation from the existing onboarding contract. Do not use Firebase Auth email/name, invitation text, caller input, cached cards or copied profile fields. The guarded backend constructs a response-only safe projection joining this name with the validated workspace relationship; there is no persisted roster-name copy or new collection. Read caller authority, assigned profiles, exact target memberships and selected account fields in one bounded Firestore read transaction. Onboarding already commits global name/revision and workspace completion atomically, so a read observes a coherent pre- or post-completion state. A pending membership in a second workspace reads the same authoritative current account name while retaining its own onboarding status. A recognized revision-zero empty account name maps to `null` only with pending onboarding; an empty name with completed onboarding, partial basics or malformed/unsupported name state fails closed. Reuse the existing 1–80-unit validated name contract for nonempty names. Refresh/reopen reads the latest committed name; no delayed trigger, fan-out or name backfill is needed. Later approved own-profile edits must retain this source/revision contract, but editing itself is not approved here.

**Why a trusted read endpoint:** Add a narrowly guarded emulator-only `clients` list/get read endpoint, reusing existing fresh Auth and native callable transport conventions behind project-owned repository/DTO interfaces. Current mobile Rules deny trainer enumeration, other-client profile reads and other-user accounts. A trusted mediator is needed to authorize the assignment and project only the approved fields from otherwise private documents. Admin bypasses Rules, so the handler repeats current verified/disabled Auth, active caller account, active workspace and exact caller trainer-membership checks on every request, independently of the UI gate. No mobile general user-document get/list or broad client-profile grant is added; existing direct Rules stay denied. Query/read only the needed source fields where supported and construct the response from named validated scalars; never serialize an account/profile snapshot, even if future sensitive keys appear. Tests must prove extra contact/health/note fields cannot escape. A persistent projection is an alternative only with a separately reviewed atomic update/migration design; it is unnecessary for this slice. Do not reuse invitation token DTOs or allow arbitrary endpoint/path strings in native bridges.

**Chosen bounded pagination design:** Recompute an **authorized-only response projection from the complete bounded active membership set on every page request**. Replace the historical `clientProfiles` candidate scan entirely; an arbitrary history scan cannot guarantee both bounded work and undisclosed hidden-only continuation. This is a transient server-side projection, not a new persisted collection or delayed authorization index. The existing trusted lifecycle caps the whole active workspace roster, including trainers: the current emulator fixture cap is **B = 5**. General lifecycle code supports a validated ceiling of 99; that ceiling does not approve a larger production cap. PR 1 reads the configured trusted cap, never a request parameter or a client-supplied count. Deployment/configuration must refuse to enable this algorithm unless its fixed transaction/read/byte budget can process the entire configured active cap, regardless of page size. No new product scope or cap is selected here.

**Bounded source read and filtering:** In the same fresh authorized Firestore read transaction, query only `workspaces/{wid}/memberships` with `status == active`, deterministic document-ID order and `limit(B + 1)`. The extra document detects a violated cap, not another UI page. Verify the complete result is at most B and agrees with the trusted activeRosterCount/revision; the count alone never authorizes or proves completeness. Validate path/schema/role for each active membership. For client members, point-read the minimal profile fields needed to validate workspace/user identity, trainerId and onboarding/createdAt. Only profiles whose trainerId equals the authenticated caller proceed to the exact active target-account/name check; project only currently authorized output rows. Other trainers' clients and inactive/revoked/disabled targets contribute no response fields or counters. Historical inactive/revoked memberships and orphan profiles are never enumerated, so arbitrarily many retained historical profiles do not consume this read budget. Invalid/missing sources cannot be repaired or treated as an authorized row.

With valid sources, there are at most B + 1 membership query documents, B profile lookups and B account/name lookups, plus the fixed caller/workspace authority reads; use field masks and bounded scalar validation rather than returning full documents. For the emulator this is at most six membership query documents and five each of the possible joins. Retrying a transaction is allowed only within a fixed retry/deadline budget. Do not add unbounded refill loops, collection-group enumeration, source-document counts or diagnostics to the public response. The minimal get action retains its same assigned-client authorization and generic inaccessible feedback.

**Fill and authorized lookahead:** After completing that bounded read, sort only authorized rows by immutable profile `createdAt ASC`, then clientId `ASC` as the unique tie-breaker. Both values come from the existing trusted profile shape; names/onboarding changes do not reorder them. Apply the authenticated cursor's last-returned tuple to this freshly authorized set in server memory. For page size 1–20, return the first pageSize authorized rows and examine the next **authorized output row** as lookahead. Issue `nextCursor` only if that extra row exists at this request's read point; encrypt the tuple of the last returned row, never a skipped or lookahead candidate. Lookahead is an authorization-checked row under the same transaction as returned rows, not the presence of any source record. Each nonterminal page is full and nonempty. If the authorized suffix has at most pageSize rows, return them with `nextCursor=null`; an empty authorized suffix is exactly `{items: [], nextCursor: null}`. No candidates, only hidden historical records, and only currently disabled/unauthorized rows produce the same empty terminal payload. Hidden rows before/between/after authorized rows cannot add pages, shorten a page or change cursor presence. No skipped-count, history-exists, scanned-count, hasMoreCandidates or per-relationship failure field is allowed.

**Scan-budget boundary and enablement prerequisite:** The algorithm always reads the complete bounded active set before publishing any page, including before claiming exhaustion. Exactly B valid active records is supported, including a disabled client whose membership still counts toward the cap. More than B active records, counter/schema drift, insufficient configured read/byte budget, transaction timeout or exhausted retries yields one generic service-unavailable result with **no page envelope, items, nextCursor, partial result, scan progress or terminal claim**. The UI keeps no new partial page and presents ordinary retry; it cannot label this as an empty/end-of-roster result. Budget/configuration failures expose no record ID/count, failed relationship or budget-specific reason; the same service-unavailable mapping applies to unrelated service failures. Configured budgets below the full cap must disable the feature at configuration time for every dataset, not fail selectively after scanning hidden rows. Under the enforced cap, hidden relationships cannot cause scan exhaustion; over-cap/corrupt state is a separate integrity outage, never a successful pagination mode. Do not silently raise B, fall back to the historical profile scan, or send an encrypted hidden-only resume token. If a future approved roster cannot fit one bounded transaction, block that enablement until an explicitly reviewed authoritative authorized-only projection with synchronous account/membership/assignment lifecycle maintenance is designed. A delayed trigger or stale projection would not suffice.

**Query/index proof:** Prove the exact status-active/document-ID membership query and bounded transaction in PR 1; this replaces the former trainerId/createdAt profile query. Sorting/pagination occur over at most B authorized-set candidates in server memory, so no name or trainerId/createdAt profile composite index is justified for this slice. Declare only any measured source-query index actually needed in the implementation PR. No index is changed or deployed here. Existing workspace cap/counter invariants and a dedicated fixture audit support the complete-read premise; production counter migration/cap approval remains a separate rollout gate. Unlike unbounded fetch-all, the total source/read ceiling is fixed independently of retained history and enforced before enablement.

**Cursor decision — confidential authenticated encryption:** Use stateless **AES-256-GCM authenticated-encrypted cursors**, sealed/opened only by the trusted read endpoint through the backend runtime's standard crypto library. Encoding or signing plaintext IDs is explicitly insufficient. Serialize the bounded canonical cursor state with an internal length prefix and pad to a fixed 4,096-byte plaintext before encryption. A fresh CSPRNG 96-bit nonce and a 128-bit authentication tag accompany the ciphertext; the only public header fields are a fixed format version and 16-byte random key identifier. Encode that fixed-size envelope as base64url with a strict 6,144-byte input ceiling. This ceiling is an input bound, not permission for variable plaintext length. Names and contact/health/note data never enter the token. Fixed-size ciphertext and fresh nonces protect the last returned authorized row tuple, its length and equality across separately issued tokens; hidden candidates never determine the continuation payload or its presence. No raw token, decrypted cursor, candidate ID or lookup reason enters logs, URLs or client diagnostics.

**Binding, expiry and validation:** Encrypt caller UID, trainer UID (must equal caller), selected workspace ID, fixed assignment filter, endpoint purpose `clients-list`, query/order and serialization versions, page size, caller membership revision, exact last-returned authorized-row `(createdAt seconds, nanoseconds, clientId)` tuple, traversal issuedAt and expiresAt. Authenticate the public header plus canonical service/environment/project, caller, trainer, workspace and requested query/order/page-size context as additional authenticated data derived by the server, never from decoded claims alone. Schema/size/path checks remain mandatory after successful tag verification. Set a maximum five-minute traversal lifetime (300 seconds); later pages preserve the original expiry rather than renewing it. Enforce issuedAt/expiresAt against the server clock with no extension on retry. Use a new query/order version for this complete-active-set contract and reject historical-scan token versions uniformly. The aggregate workspace roster revision is not included or compared as a cursor condition, so adding/removing hidden relationships cannot itself signal their existence through token validity. A cursor can be replayed only within its lifetime and scope, with fresh authorization; it is neither a role grant nor a snapshot token.

For each page, refresh verified/disabled Auth and independently re-read active caller account, active workspace and valid path-bound trainer membership. Reject changed caller authority revision, then rebuild the complete bounded authorized-only projection above, including fresh candidate assignment/account/membership validation for returned rows and lookahead. A token successfully decrypting never substitutes for those checks. The last-returned tuple is an authenticated position only: **do not point-read or validate anchor existence/assignment**, and do not accept a caller-supplied anchor override. Compare that tuple against the freshly projected rows in memory even if the formerly returned record is now absent or ineligible. This removes the historical-assignment oracle. If no authorized row remains beyond the tuple, return the terminal payload; hidden remaining sources never justify a continuation. A token issued after one request's authorized lookahead may therefore lead to an empty terminal page if that row loses access before the next request. That is current authorization changing, not an empty hidden-candidate continuation.

**Uniform invalid-cursor behavior:** Tampering with any header/nonce/ciphertext/tag byte, unknown/retired key, unsupported version, malformed payload, oversized input, foreign caller/trainer/workspace/environment/query/page size, expired/future-issued token and caller-revision mismatch all use the same public invalid-cursor error code/status and body: reload the roster. Return no items, cursor echo, client ID, sort tuple, failed check or historical-existence hint. Verify authentication before parsing decrypted state or touching target records; there is no anchor-validation endpoint or reason-specific response. Ordinary Auth/access denial stays the existing safe gate independent of supplied cursor contents, with no target information. Use the same failure mapping whether the guessed anchor names a current, revoked, moved, disabled, deleted or never-existing client; no anchor lookup is performed at all. Successful page fullness/continuation must depend only on currently authorized output, not hidden sources; expose no skipped-count or per-client reason metadata. This is a response-field confidentiality contract, not a claim of constant-time database execution.

**Key lifecycle and environment configuration:** Emulator PR 1 generates a random 256-bit encryption key and random 16-byte key ID in the guarded loopback demo backend at process startup, keeps them in server memory only, and invalidates that generation on restart. Rotate the issuing key after one hour or 2^20 issuances, whichever comes first; require a fresh random nonce for every seal, stop issuing before the cap, and retain a prior decryption key only until its last issued cursor's maximum 300-second lifetime ends. Retired/unknown keys fail uniformly; suspected compromise removes the key immediately, requiring roster reload. This bounded random-nonce budget and rotation are engineering requirements to verify in PR 1. Do not persist keys in source, fixtures, mobile binaries, logs or cursor content, and never accept caller-selected key material. Owned test-process teardown drops the key ring; there is no server cursor-handle store or new recovery queue.

Before any separately authorized production enablement, platform/security must provision a protected, environment-isolated versioned key ring with coordinated issuance/rotation across all serving instances, a single issuance budget per key, bounded old-key decryption and clock monitoring. Production must explicitly configure a finite lifetime no greater than 300 seconds and enforce the same wire/nonce/rotation contract; it must fail closed without that protected configuration, never fall back to the ephemeral emulator key or reuse a demo key. Emergency retirement and normal rolling rotation require operational tests. These are future production gates, not approval of deployment, retention policy or wider visibility, and not prerequisites for the single-process emulator slice. Neither rotation nor a restored key can make an expired/denied cursor authoritative.

Ordering remains stable when a name or onboarding state changes. Pages and lookahead share one coherent transaction read point, but different requests are not a traversal-wide snapshot; refresh replaces all pages and deduplication uses clientId. Membership/lifecycle writers retain the existing atomic workspace membershipRevision/counter protocol, and any future assignment writer must preserve the complete-read invariant. That aggregate revision is internal concurrency/integrity evidence, not a cursor claim or public invalidation signal: hidden relationship changes must not produce a different cursor-validity response. Only the caller’s own authority revision is bound to the cursor. Target membership revocation, assignment change or account disablement instead changes the freshly projected authorized rows before filling or lookahead; it does not by itself cause a hidden-change-specific reload. Current reassignment remains excluded. Account re-enablement similarly restores only currently authorized rows; rows at/before the previous returned tuple require refresh to be seen. Do not promise a mutation-free snapshot, stable total or complete traversal across such changes. Revocation/account disablement/workspace suspension committed before the read point denies or omits affected data. A later revocation cannot retract bytes already returned. Caller authority/lifecycle listeners cancel and clear protected pages/details and fence late replies; target re-open/refresh always reauthorizes and clears a now-denied detail. Reconnect/foreground rechecks the existing gate before a fresh request. There is no promise of continuous per-client notifications or immediate discovery of remote revocation while disconnected, and no offline roster grant: cached names/status and cursors cannot reopen a protected shell. OS notification acceptance remains a carried closeout gate.

**Mutation and recovery:** No business mutation, receipt or ledger preparation. Read retries are idempotent; cancellation fences late results and creates no critical work that blocks departure. Keep response pages transient within the verified scope, clear them on loss/switch/background, and do not introduce a new persistent name cache, raw payload logs or retention promise. Offline uses the existing ConnectToVerify/Locked Recovery root. Original invitation/onboarding recovery, freeze and cleanup remain unchanged.

**UI/tests/acceptance:** Use `FOi6s`/`bLqqR` reduced to approved names and relationship/onboarding status. Cover loading, unnamed pending, empty/final, filled pages with authorized lookahead, budget-unavailable without a partial page, page retry, cursor-invalidated refresh, inaccessible detail and offline states. Backend tests must prove cross-trainer denial even with another active trainer membership in the same workspace (an adversarial fixture, not multi-trainer product enablement), cross-workspace/cross-client/forged caller denial, path/role/schema mismatches, source-field injection without leakage, equal-createdAt tie-breaking, bounded reads, invalid/foreign/stale encrypted cursors, skipped revoked candidates, name changes and concurrent onboarding, revocation/disablement/suspension races. The dedicated cursor acceptance cases below are mandatory. Prove existing direct account/profile/list/write denials remain intact. Shared MVI tests cover page ordering, continuation/dedup, reset and UID/workspace/epoch disposal. Both Android SDK transport and native Swift bridge execute real list/get, cold restore, foreground/reconnect, scope loss and clean sign-out checks; actual normal/200% touch, Back, keyboard and TalkBack/VoiceOver are required for slice acceptance. Names may appear only in the approved UI, never raw diagnostics or unrelated summaries.
