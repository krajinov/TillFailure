This documentation/publication task does not authorize implementation.

Milestone 4 remains unaccepted for the [closeout gates](milestone-4-closeout.md#remaining-gates-and-classification). Independent client-management development does not waive those gates, and unrelated production decisions are not prerequisites for local emulator development.

## Proposed sequential PRs

### PR 1 — Online named roster and minimal assigned-client details

**User outcome and approved scope:** An active trainer opens Clients, pages through their own assigned active clients by name, and opens minimal relationship/onboarding details in the selected active workspace. Josip approved this narrow read behavior on 2026-10-17. The same workspace does not entitle a trainer to another trainer's clients. Pending-onboarding clients may not yet have a name; show an honest “Name not provided yet” label rather than inventing one or exposing contact information.

**Included/excluded and minimal payload:** Each list item and detail returns exactly `clientId`, `workspaceId`, `displayName` (validated string or `null` for the recognized unnamed bootstrap state), `relationshipStatus=active`, and `onboardingStatus=pending|complete`. IDs are navigation identity, not grants. Revisions and pagination sort values remain cursor/internal consistency metadata, not additional client profile fields in the UI. A page envelope adds only `items` and `nextCursor`; no total-client or attention counts. Exclude contact information/email/phone, health, notes, search, profile editing, reassignment, membership/lifecycle actions, photos, joined/since dates and all later-milestone metrics. Existing own-client Profile remains intact.

**Authoritative assignment and status:** `workspaces/{wid}/clientProfiles/{clientUid}.trainerId` is the trusted assignment source, created from the verified inviter by invitation acceptance. It must equal the authenticated caller UID; neither a request's trainerId nor a workspace owner field substitutes for it. Validate profile schema, stored workspace/user IDs against its path and supported onboarding shape/revision. Relationship status comes from the exact path-bound `workspaces/{wid}/memberships/{clientUid}` with client role; onboarding status comes from that workspace profile. Both caller and target accounts must be active/schema-current, the workspace active/schema-current, and both memberships valid at their exact paths. An assigned profile alone never grants access after membership revocation. Reassignment is excluded; any future assignment writer must define authorization and cursor invalidation explicitly.

**Authoritative name and consistency with onboarding:** The sole name source is `users/{clientUid}.displayName`, with its `profileRevision` and recognized bootstrap validation from the existing onboarding contract. Do not use Firebase Auth email/name, invitation text, caller input, cached cards or copied profile fields. The guarded backend constructs a response-only safe projection joining this name with the validated workspace relationship; there is no persisted roster-name copy or new collection. Read caller authority, assigned profiles, exact target memberships and selected account fields in one bounded Firestore read transaction. Onboarding already commits global name/revision and workspace completion atomically, so a read observes a coherent pre- or post-completion state. A pending membership in a second workspace reads the same authoritative current account name while retaining its own onboarding status. A recognized revision-zero empty account name maps to `null` only with pending onboarding; an empty name with completed onboarding, partial basics or malformed/unsupported name state fails closed. Reuse the existing 1–80-unit validated name contract for nonempty names. Refresh/reopen reads the latest committed name; no delayed trigger, fan-out or name backfill is needed. Later approved own-profile edits must retain this source/revision contract, but editing itself is not approved here.

**Why a trusted read endpoint:** Add a narrowly guarded emulator-only `clients` list/get read endpoint, reusing existing fresh Auth and native callable transport conventions behind project-owned repository/DTO interfaces. Current mobile Rules deny trainer enumeration, other-client profile reads and other-user accounts. A trusted mediator is needed to authorize the assignment and project only the approved fields from otherwise private documents. Admin bypasses Rules, so the handler repeats current verified/disabled Auth, active caller account, active workspace and exact caller trainer-membership checks on every request, independently of the UI gate. No mobile general user-document get/list or broad client-profile grant is added; existing direct Rules stay denied. Query/read only the needed source fields where supported and construct the response from named validated scalars; never serialize an account/profile snapshot, even if future sensitive keys appear. Tests must prove extra contact/health/note fields cannot escape. A persistent projection is an alternative only with a separately reviewed atomic update/migration design; it is unnecessary for this slice. Do not reuse invitation token DTOs or allow arbitrary endpoint/path strings in native bridges.

**Queries, ordering and indexes:** Query only `workspaces/{wid}/clientProfiles` with `trainerId == authenticatedCallerUid`, ordered by immutable `createdAt ASC`, then document ID/clientId `ASC` as the unique tie-breaker. Both fields exist in the accepted invitation profile shape; do not sort by names or depend on membership joinedAt, which lifecycle replacements may omit. Use `startAfter(lastCreatedAt, lastClientId)`, page size 1–20 and at most `pageSize + 1` candidate profiles per request. Process at most `pageSize` candidates; the extra is lookahead. Check each processed candidate's exact membership/account before returning it. Valid revoked/inactive/disabled targets are omitted without their names or status being returned; malformed or identity-inconsistent source data fails the page safely. Cursor advancement follows the last processed candidate, including omitted ones, so no unbounded refill/scan is needed. A page can have no visible items and still have `nextCursor`; the UI offers continuation and must not declare the roster empty until traversal ends. Do not show counts of omitted clients. The get action uses direct profile/member/account lookups with the same predicate and generic unavailable feedback for missing, inactive, foreign-trainer or foreign-workspace IDs. No client collection-group query or fetch-all workaround.

Prove the exact collection query and index definition during PR 1. The anticipated collection composite is trainerId/createdAt with document-ID ascending tie-breaking; add only what the measured query needs in that implementation PR. The checked-in membership group index and proposed displayNameNormalized profile index do not supply this contract. No index is changed or deployed by this documentation task. Validate dedicated fixture profile creation times/IDs before the walkthrough; unsupported or missing ordered fields cannot authorize reads or be silently synthesized to claim completeness. Production data inventory/migration remains a separate rollout gate.

**Cursor validation and freshness:** Use an encoded, strictly validated, versioned scope-bound cursor carrying caller UID, workspace, fixed trainer filter, query/order version, page size, caller membership revision, workspace membershipRevision and the last processed `(createdAt, clientId)` tuple. Preserve timestamp seconds/nanoseconds exactly. Enforce a finite encoded-size bound, exact keys/types/ranges, safe path segments and exact scope/order/filter/page-size equality; derive the trainer filter from Auth even after cursor validation. Verify the anchor profile belongs to this trainer/workspace and its immutable sort tuple matches. Foreign, malformed, changed-anchor or mismatched-version cursors return a generic invalid/reload state without target data. Compare current authority and workspace revisions on every request; a change invalidates the cursor and restarts from page one. No cursor signature or possession bypasses current authorization, and no opaque server cursor store/new retention policy is required for the validated-cursor design.

Ordering remains stable when a name or onboarding state changes. Pages are fresh at each transaction's read point, not a permanent snapshot across the whole traversal; refresh replaces all pages and deduplication uses clientId. Revocation/account disablement/workspace suspension committed before the read point denies or omits affected data. A later revocation cannot retract bytes already returned. Caller authority/lifecycle listeners cancel and clear protected pages/details and fence late replies; target re-open/refresh always reauthorizes and clears a now-denied detail. Reconnect/foreground rechecks the existing gate before a fresh request. There is no promise of continuous per-client notifications or immediate discovery of remote revocation while disconnected, and no offline roster grant: cached names/status and cursors cannot reopen a protected shell. OS notification acceptance remains a carried closeout gate.

**Mutation and recovery:** No business mutation, receipt or ledger preparation. Read retries are idempotent; cancellation fences late results and creates no critical work that blocks departure. Keep response pages transient within the verified scope, clear them on loss/switch/background, and do not introduce a new persistent name cache, raw payload logs or retention promise. Offline uses the existing ConnectToVerify/Locked Recovery root. Original invitation/onboarding recovery, freeze and cleanup remain unchanged.

**UI/tests/acceptance:** Use `FOi6s`/`bLqqR` reduced to approved names and relationship/onboarding status. Cover loading, unnamed pending, empty/final/empty-with-continuation, page retry, cursor-invalidated refresh, inaccessible detail and offline states. Backend tests must prove cross-trainer denial even with another active trainer membership in the same workspace (an adversarial fixture, not multi-trainer product enablement), cross-workspace/cross-client/forged caller denial, path/role/schema mismatches, source-field injection without leakage, equal-createdAt tie-breaking, bounded reads, invalid/foreign/stale cursors and anchors, skipped revoked candidates, name changes and concurrent onboarding, revocation/disablement/suspension races. Prove existing direct account/profile/list/write denials remain intact. Shared MVI tests cover page ordering, continuation/dedup, reset and UID/workspace/epoch disposal. Both Android SDK transport and native Swift bridge execute real list/get, cold restore, foreground/reconnect, scope loss and clean sign-out checks; actual normal/200% touch, Back, keyboard and TalkBack/VoiceOver are required for slice acceptance. Names may appear only in the approved UI, never raw diagnostics or unrelated summaries.

**Dependencies/gates:** Existing provisioning, invitation acceptance, minimal onboarding and path-bound identity sources support this contract. The read endpoint, source projection/validators, exact query/index/cursor and both native adapters are engineering deliverables of PR 1, not existing capabilities. The narrow visibility approval is complete; no new product decision or external production prerequisite blocks starting local implementation. Closeout G1–G11 remain open in their affected scopes. Production deployment, retention, wider visibility, sensitive fields and mutations require their separate decisions. This task does not implement PR 1.
