## Authority and atomic transaction

`clientRevocationEmulator` exposes only `prepare-client-revocation` and `revoke-client` under named demo/loopback guards. Every callable invocation verifies a fresh non-anonymous bearer with token-revocation checking, derives UID from Auth, and reloads enabled verified Admin Auth. The transaction requires an active schema-current caller account/email/lifecycle, active owner workspace, exact active trainer membership/profile/directory, and exact target client membership/profile assigned to that caller. An unrelated owner, non-owner assigned trainer, self-action or client cannot revoke. Target global account may be active or disabled; target Auth need not be enabled. The unchanged PR 1 roster/details read contract still hides already-disabled global targets; the backend removal contract and a target-disable race after authorized details do not broaden that read visibility. No identity/account repair or target account write occurs.

Preparation is read-only, returns target UID plus four expected revisions, and grants no later authority. The command preserves exact workspace/target, target membership revision, workspace membership revision, caller membership revision and caller lifecycle revision. It does not bind to global profile revision, preventing unrelated profile changes in another workspace from becoming a mutation precondition. All source bindings, arithmetic and discovery state are validated before a new success or conflict decision. Malformed sources cannot be turned into a durable conflict.

Success performs exactly five writes in one transaction: update only target membership status/contribution/revision; delete only its discovery reference; update only its catalog count/status/revision; update only selected workspace counters/membership revision; create the immutable caller-bound receipt. Existing `projectMembershipCounters` and `contributionChange` supply the arithmetic and no-new-access entitlement behavior. Membership joinedAt/invitation provenance, target profile/onboarding, Auth/global basics and other memberships/accounts remain untouched. Disabled targets are removable without re-enabling catalog access.

A recognized stale command records only an immutable `revocation-conflict` receipt. Replays recheck current caller/resource authorization before returning a strictly validated self-contained success/conflict, without requiring the target still active or old expected revisions still current. Generic rejection, malformed state, assignment artifacts, service errors and missing receipts remain ambiguous; no discard or automatic revision replacement occurs.

Work is fixed: at most 12 fixed source/config/receipt paths, a complete active-roster query capped at six results (fixture cap five), and two one-document artifact probes, at most 20 returned source documents per attempt, three attempts and a five-second elapsed-work check before writes. This is an elapsed-work bound, not cancellation of an outstanding RPC. Firestore source documents each have its service size limit; there is no unbounded traversal or invitation/history scan. The five targeted writes and bounded receipt introduce no fan-out, arbitrary audit content or client-supplied limits. Existing fixture caps remain two contributions/five active members. No Rules/index/dependency change is made.

## Publication serialization and history boundary

Both selected-workspace probes reject any account-owned assignment header or matching workspace index for the client, including terminal artifacts. Other-workspace artifacts are independent. The isolated assignment materializer now requires current active workspace, exact active client and trainer memberships, matching profile/trainer/caller, and advances workspace membershipRevision atomically with artifact creation. Publication and revocation both read/write this same revision; an empty query alone is not the fence. Publication-first leaves artifacts and makes revocation reject; revocation-first makes publication reject its live membership checks; competing transactions cannot both commit. Publication adds one budgeted workspace write (ordinary fixture publication nine writes, replacement eleven). Existing receipt replay performs no new publication writes. Close/replace retain artifact identities; raw Admin writes and unaudited old materializers remain outside the trusted contract and cannot be made safe by UI/query checks.

The trainer-index Rules predicate gap is deliberately retained and regression-tested: an otherwise eligible trainer may still read an existing index after the client's membership changes. PR 4 rejects every such artifact-bearing target and does not claim to fix that historical-access policy. No new coaching-history grant is introduced. Old acceptance replay/tokens and a new same-pair invitation cannot restore retained membership/profile state; no automatic invitation/program/booking cancellation or deletion occurs.

## Seventh protected command and native/UI integration

The seventh variant is `revoke-client`, canonical kind `client-membership-revoke`, hash format `client-revocation-v1`, policyVersion 1. Its strict nested `revocation` descriptor and minimal success/conflict decision adapters preserve the existing caller/key `lifecycleCommands` identity and whole-key consumption invariant. Applied, conflict and covered absent/fenced outcomes use the existing seven-field own-outcome projection. Fresh original global identity can resolve after workspace membership/ownership loss; it receives no resource data or role restoration. All earlier six variants and shared-namespace writer guards remain in place. Stable generation/provenance, finite request/fence budgets, legacy/identity/storage limitations and trusted intact-history assumptions remain those of [PR #13](milestone-5-command-resolution-report.md), not automatic history-loss proof.

The existing encrypted account envelope gains optional `revocation` in its single pending command. The same ledger, terminal proof, proof-before-retirement writes, last-proof validation, issuance/freeze locks and clean-departure ordering apply; no new recovery store/coordinator is added. Normal and resolver callbacks match every bound field before retirement. Newer pending work and account B remain protected. Retry preserves the exact key/payload and stops after durable resolution start; Resolve uses the existing explicit confirmation. Older decoders must lock on unsupported fields rather than replace work.

Authorized client details load a fresh preparation. The action appears only for eligible preparation and is labeled “Revoke client access to this workspace”. Confirmation identifies the already-authorized client and selected workspace, with an authorized client reference when no name exists yet, and explains immediate access loss, preserved account/other workspaces/records, no Undo/re-invitation and protected pending work. Scope/authority epoch, detail visit generation, exact revisions and prompt identity fence confirmation, cancellation and duplicates. Issuance persists the command before transport. Success clears detail and emits a consumption-fenced effect that recreates/reloads the authorized roster; later refresh failure cannot resubmit the settled command. Conflict requires explicit refresh and reconfirmation; unconfirmed work links to existing Invitations/recovery.

Known client authority loss retires presentation through existing monitoring/revalidation. Auth remains signed in; no automatic workspace change is issued. The existing explicit Change workspace action re-verifies the remaining membership. Account/workspace choice never rebinds pending commands.
