### Content and lifecycle details

Preserve approved scalar validation: no normalization/trimming/truncation, isolated surrogates or C0/C1 controls; canonical interior LF only in multiline fields. Sets 1–20; reps 1–1,000; rest 0–3,600 seconds; load null or 0–1,000,000 integer grams with exact kg UI conversion. Require all existing UUID/unique-item/stable-order rules. No AMRAP/failure token, ranges, duration/distance, RPE/RIR, percentages, per-set arrays, weeks/schedule/progression, per-item coaching notes or new units.

Published content is the complete saved title/description, workout IDs/titles/order and item IDs/order. Each item copies its saved source tuple/name and exact prescription, plus the matching source's `instructions`, `muscleGroups` and `equipment`. System instructions retain the existing 2,000-scalar/8,000-byte ceiling; system arrays retain their original order, at most eight distinct labels of 40 scalars each. Custom instructions have the same text ceiling; each custom array remains the existing sorted, at-most-three allowed taxonomy tokens with the bodyweight exclusivity rule. The draft's 650-scalar budget continues to cover only its existing text fields; adding instructions/taxonomy to immutable versions does not enlarge the draft/source limits.

Do not copy system `nameNormalized`, status, source timestamps, custom mutable revision metadata beyond `sourceRevision`, source authority records, media, client IDs, health/profile/note data, credentials or unknown fields. Hashes bind the original source definitions even where some fields are not published. Immutable owner/workspace in the version provides custom-source tenant provenance; a system source ID is global. `publishedAt` is a server Timestamp; `ownerUid` is also the sole permitted publisher, so no redundant `publishedBy` is needed. Version identity/number, saved draft revision/hash and content hash complete provenance. Version browsing renders the stored copy without live source reads, links granting source access, or overlays from corrected sources.

Previously published content is never rewritten when the draft, system source or custom source changes. Current source authorization is required for **new** publication; current source entitlement is not required to read an already-published retained copy under U1. Withdrawal/suspension removes author access, not stored content. Restoration never changes owner or rebinds submitted commands. Disabled/deleted/unavailable global identity or damaged storage keeps the existing lock; no automatic historical restoration of private trainer notes is implied.

Publication neither assigns a program nor grants clients access. Future M7 may select an exact retained version and materialize a client-safe account-owned copy with its own authorization, schedule, horizon, hash, expiry and recovery decisions. Source revision, latest pointer and current source availability must not become permission to mutate an existing assigned copy. The isolated assignment primitive and its index limitation remain unresolved M7 integration work, not PR 4 blockers. No guarantee is made that this prescription vocabulary or layout satisfies every future assignment requirement.

## Smallest proposed protocol

### Root transition and immutable version layout

Choose one **inline immutable version document** at `workspaces/{wid}/programTemplates/{templateId}/versions/{versionId}`. It contains ordered bounded arrays, not unbounded history. No workout/item children, summary duplicate, staging document, content blob or mutable payload pointer is needed; the measured comparison below supports this choice.

Existing schema-1 roots remain valid, with implicit versionCount 0/currentVersionId null. On first successful publication, atomically transition that root to schema 2, preserving every existing field and adding **exactly** `versionCount` and `currentVersionId`. Keep `policyVersion:1` for the unchanged draft content policy. Schema 2 requires `versionCount` in 1..2147483645, `versionCount < revision`, and `currentVersionId == "v" + decimal(versionCount).padStart(10,"0")`. No schema-2 zero/null hybrid. Subsequent Save must preserve these fields from the transactional root, never accept them from the client, and never downgrade the schema. Schema-1 Save remains schema 1 until first publication. Both schemas use the same `revision` and immutable creation metadata.

This is a required compatibility change: the current exact `definition()` validator and full replacement Save would otherwise reject or erase publication metadata. Update root readers/validators/Save preservation deliberately; retain **unchanged** `save-program-draft` descriptor/hash/result semantics and receipts. Preexisting pending Saves either replay their original receipt or get an ordinary newer-root conflict. Older app/server schema readers must fail closed; do not strip fields to run an older build. Rollback can hide new issuance but must retain schema-2 reads/preservation, receipts and recovery or explicit safe locks.

Version exact fields:

```text
schemaVersion: 1
contentPolicyVersion: 1
workspaceId, templateId, ownerUid
versionId: "v" + ten decimal digits; equals versionNumber-derived path
versionNumber: integer 1..2147483645
draftRevision: integer 1..2147483645 (root revision before publication)
draftHash, contentHash: lowercase 64-hex SHA-256
publishedAt: server Firestore Timestamp
title, description
workouts: [{id, title, items: [{
  id, sourceKind, sourceId, sourceRevision, sourceHash, name,
  prescription: {sets, reps, restSeconds, loadGrams},
  instructions, muscleGroups, equipment
}]}]
```

Read DTOs replace only `publishedAt` with `publishedAtMillis`. The `versionNumber <= draftRevision` invariant follows from at least one initial Save and one root advancement per publication; repeated Saves can make the inequality strict. No mutable status field exists on a version. `tx.create`, a unique version path and no version-update/delete handler enforce immutability. Unexpected preexisting next-version paths, missing roots, regressed revisions or malformed metadata are integrity failures, never overwritten or auto-repaired. Historical versions are independent documents; appending a version does not rewrite a version manifest or scan all history.

### Exact descriptor and hash definitions

New action **`publish-program-template`**, protected kind **`program-template-publish`**, request-hash version **`program-publication-v1`**. Exact descriptor, with no extra keys:

```text
{
  action: "publish-program-template",
  workspaceId: existing strict single-segment identifier (<=128 UTF-16 units),
  idempotencyKey: existing covered or1-generation key (nonce 1..80 ASCII chars),
  publish: {
    templateId: existing lowercase version-4 UUID,
    expectedRevision: integer 1..2147483645,
    authority: {
      authorLifecycleRevision, authorMembershipRevision, workspaceMembershipRevision
    },
    draftHash: lowercase 64-hex SHA-256,
    contentPolicyVersion: 1
  }
}
```

Authority integers remain 1..2147483646. Caller UID comes only from verified Auth. Use existing `stableHash`/shared canonicalization: sort object keys, preserve array order, exact Unicode and explicit nulls, UTF-8 SHA-256; fixed ASCII key names avoid locale-dependent key-order ambiguity. Do not invent a new hash algorithm or change old ones.

Define `B = {contentPolicyVersion:1, workspaceId, templateId, ownerUid, title, description, workouts}`, where workouts are the **saved draft arrays**, including every existing item field/null. `draftHash = stableHash({hashVersion:"program-draft-content-v1", ...B})`. Exclude root schema, timestamps, revision and version metadata; revision is separately and mandatorily bound by `expectedRevision`. This is a new projection hash, not the old Save command hash. Hashing a freshly loaded arbitrary draft without comparing the submitted hash is forbidden.

Let `C` be B with instructions/taxonomy appended to each item from matching sources using the exact U3 projection. `contentHash = stableHash({hashVersion:"program-version-content-v1", ...C})`. Exclude version identity/number, draft revision/hash and publication time; two intentionally identical publications can have the same content hash and different version IDs. All content decisions are fixed by descriptor policy 1, saved hash/revision, existing source fingerprints and immutable projection code. Policy-1 behavior must not drift after preparation; later content-policy changes need a new version and explicit support or rejection of old pending policy, never silent reinterpretation.

`requestHash = stableHash({...descriptor, callerUid, policyVersion:1})`; `commandId = stableHash({callerUid,idempotencyKey})`. Resolver request remains `{protocolVersion:1,descriptor}`. Source arrays need not be duplicated in the command: their complete fingerprints are already inside the committed draft hash. There is no “publish whatever exists” path, mutable staging pointer, timestamp-based source selection or server default for a missing hash.

The sizing script emits a reproducible synthetic hash vector: caller A, workspace w, template `00000000-0000-4000-8000-000000000001`, expected/authority revisions 1, policy 1, draftHash 64 `a` characters, key `or1-b91f0176ec74475e8cf7406e25b7e9d3-publication-vector`. Command ID is `f3305d4ae3cd01f3ff117fb22b54b078b2bda261d9632501087de6552b883f6c`; request hash is `9f2f8f049c555ec488c4e01388432921094a3250b348175081a665338cb0584c`. These are current TypeScript hash results on a proposed descriptor, not proof of a future Kotlin adapter. Freeze cross-language vectors before issuance.

### Preparation, confirmation and transaction

1. **Fresh prepare** accepts only workspace/template IDs, via a fixed guarded mediator. Verify fresh non-anonymous, enabled, email-verified, revoked-token-checked Auth and global email binding. In one read transaction check the five existing authority documents: account, workspace, exact trainer membership, own trainer profile and own membershipRef. Reuse their exact schema/status/role/contribution/revision checks. Load the saved root; reject foreign/missing equivalently. Validate completeness and every source, deduplicating up to twelve paths. Return bound publish fields, next version number and complete transient preview C/contentHash. No write other than ordinary rate admission; no prepared payload is stored server-side.
2. **Confirm exact preview.** UI independently validates/hashes the saved projection and preview; freezes the returned authority/revision/hash/policy. Derive B from preview C by removing only instructions/muscleGroups/equipment from each item, and verify draftHash; recompute contentHash over C. Show saved title/version number, exercises, prescriptions and copied text. Dirty edits require explicit Save and successful settlement/reload first. Cancel/Back before confirmation sends no protected command. A changed preview requires a new confirmation, never a silent refresh at send time.
3. **Durably prepare the small command.** Generate one covered key; under the existing native UID/generation/freeze ownership lock, perform complete prospective admission and persist before transport. Capture no copied publication text in the pending descriptor. A later root change is a conflict, not permission to update this descriptor.
4. **Transactional issuance.** Recheck the generation/provenance guard, five authority records and exact submitted tuple. Read the whole-key receipt and root. A matching immutable business receipt returns its original decision without source reads/effects; an own-command fence prevents every effect, and a changed kind/hash/key binding fails closed. Normal replay requires current original authority as existing business commands do; own-resolution is the way to learn the historical outcome after authority loss.
5. **Validate expected state.** Root revision greater than expected produces a durable revision conflict. At equal revision, recompute B/hash and require equality. Validate U2 completeness, then load **every** unique source and optional fixed systemCatalog entitlement transactionally. Do not use Save's unchanged-selection exemption. Require each `sourceIdentity` selection/name to equal the saved tuple, active published system status and entitlement, or exact same-author/workspace custom definition. All reads precede writes.
6. **Materialize and commit atomically.** Derive C/contentHash and next count/ID from the matched root, validate complete output/byte/index budgets, and check revision/counter/time ceilings. One transaction creates the immutable version, replaces the root with unchanged draft content plus advanced revision/pointer/counter/updatedAt, and creates the minimal immutable receipt. First publication alone upgrades root schema. No workspace revision, assignment, client index, source record or entitlement is written. Abort means none of these three writes committed.

Source fingerprints use the current production `sourceIdentity`: system hashes include schema/name/nameNormalized/instructions/label arrays/status and source kind/ID; custom hashes include kind/workspace/ID and schema/policy/owner/name/instructions/taxonomy/revision, excluding timestamps. System content or array-order changes cause conflict even without a revision field; custom revision advancement causes conflict even if visible text is restored. Custom timestamp-only changes do not affect the content fingerprint, but malformed timestamp order still fails source validation. A system source changed and restored byte-for-byte is indistinguishable from unchanged content; this policy binds exact current content and authorization, not a history of every intervening system edit. Do not promise revision history the schema lacks.

Source correction/deletion/status loss, entitlement loss, or malformed/foreign source after preparation yields the same minimal source-conflict category while the author still has template authority. Do not echo inaccessible names, source documents or which foreign path exists. Saved copies remain intact. Explicit picker replacement/repair and Save are needed before another publication. Authority/role/lifecycle changes instead deny business issuance without inventing a success/conflict receipt; the original command remains recoverable through existing eligible own-resolution. Firestore authority/source changes serialize with the transaction; external Firebase Auth disable and Firestore commit are not one cross-service atomic operation. Retain that residual boundary and recheck on each operation.

### Concurrency and repeated publication

| Race / event | Required result |
|---|---|
| Save and Publish expect revision r | If Save wins, Publish receives durable revision conflict. If Publish wins, Save receives its existing draft conflict. Exactly one root advancement/effect wins; no publication of the later draft. |
| Two Publish commands expect r | One creates v(n+1) and root r+1; the other records revision conflict without another version. Same key/hash returns the one original result. |
| Same key after lost acknowledgment | Original receipt decides; no new count, time or version. Replaying after later publication still returns the original version, never the current pointer. |
| New explicit Publish at freshly prepared r+1 | Creates another version, even if contentHash is identical, under U4. A generic retry button must never create this new command. |
| Source/authority changes during retry | Re-read within the transaction; content mismatch conflicts, changed authority denies. Never update the submitted hash or tuple inside retry. |
| Continue editing after publication | Draft content remains in place. Fresh root get establishes r+1, and later Save preserves publication fields. Old version hashes/bytes stay unchanged. |

## Recovery and immutable decisions

Exact schema-1 business receipt fields: `{schemaVersion,commandKind,callerUid,workspaceId,templateId,requestHash,result,committedAt}`. Kind is `program-template-publish`. `result` always has exactly `{status,workspaceId,templateId,templateRevision,versionId,versionNumber,contentHash}`; use explicit null for all three version fields on conflicts. `replayed` is a transport acknowledgment boolean, not a stored result field.

| Status | Validation / effect |
|---|---|
| `program-published` | templateRevision = expectedRevision + 1; versionNumber 1..expectedRevision; versionId equals its padded number; contentHash is 64-hex. Version/root/receipt committed together. |
| `publication-conflict` | Observed templateRevision > expectedRevision, within existing revision ceiling; all version fields null. Receipt only. |
| `publication-draft-conflict` | Equal revision but different canonical draftHash; all version fields null. Receipt only; never silently publish current content. |
| `publication-source-conflict` | Equal revision/hash but source selection/current authorization cannot match; version fields null. Receipt only. |
| `publication-incomplete` | Equal revision/hash, valid saved draft fails U2; version fields null. Receipt only. Normally prevented by prepare; retained to safely settle direct/stale business requests. |

Malformed input/root/infrastructure, lower/missing root revision, wrong owner, exhausted counters, invalid clocks, unknown schema and generic server errors are unavailable/denied, not manufactured terminal receipts. A valid same-revision hash mismatch is deliberately an explicit immutable non-application decision, not proof of storage corruption. Conflict receipts reveal only the already-bound own template and permitted revision. Strictly validate allowed keys/types, caller/key/hash, path IDs, result relationships and timestamp before accepting any proof.

Own-resolution adds one adapter: applied status maps to `applied`; the four conflicts map to `not-applied-conflict`; existing schema-2 whole-key fence maps to `not-applied-fenced`. Reply stays exactly the existing seven fields `{protocolVersion,commandKind,commandId,requestHashVersion,requestHash,outcome,decidedAtMillis}`. **No version ID, number, content hash, template/workspace/source identity, authority, title or copied content is returned by own-resolution.** Validate the receipt without reading a live root/version/source/workspace. Current eligible original global identity is sufficient even after workspace/role/source loss. Fresh authorized version browsing after settlement finds the result; a minimal resolver success alone cannot reopen an old feature screen or grant content access.

Audit every publication writer before extending covered-generation absence resolution. Keep existing generation/provenance history checks, per-caller fence budget at most 100, caller/key-wide IDs and immutable receipts. Commit-first resolution observes the receipt; resolver-first creates the whole-key fence in the same namespace before any delayed issuance. Missing legacy history/unsupported generation/identity remains locked. No TTL, fence removal, new generation over damaged history or rekey-to-retry shortcut is authorized.

Persist the exact descriptor/UID/key in the existing encrypted pending slot, with both resolutionStarted states supported. On normal acknowledgment or own-resolution, first persist the full command plus validated terminal proof. Only then retire into existing `compacted-v1` with schema-1 marker: UID, kind, command ID, hash version/hash, source, outcome and resolver decision time only when supplied. Normal proofs invent no decision timestamp. Retired publication marker contains no raw key, workspace/template/version/source identity, draft/content hash as separate fields, authority, text or prescription. Its requestHash commits to the command but grants no access. A marker is never a replacement for pending proof.

Proof-write failure retains original pending state; retirement failure retains the durable full proof; restart completes only the verified transition. Old seven full-proof variants stay full; note/custom/draft markers and supported old full forms remain compatible. No history is cleared to fit. Freeze → prove empty → drain → durable departure marker → fence/dispose → sign-out → terminate/clear/proven cleanup → completion/next account remains unchanged. Unknown outcome, storage ambiguity or failed proof blocks account departure. Presentation cancellation cannot revoke an issued Publish or suppress valid account-owned settlement.

SDK transaction metadata/framing varies. **256 KiB is a conservative new-publication request reserve to verify in implementation**, not an enlargement of the old Save's 64 KiB reserve, a measured network maximum, or an SDK cap. No file changes to old caps. Enforce complete output/protobuf estimates before writes; measure the actual mediator request before enabling issuance. A ceiling miss must be reviewed, never silently accommodated by splitting.

**Concrete read-cap requirement:** Android's draft HTTP reader and Swift `callProgramDrafts` reject packets above 64 KiB; shared `DraftReads.callable` also caps the wrapper at 64 KiB and `draft-get` at 24 KiB. The system catalog's unrelated 256 KiB packet limit is not a reusable publication grant. An inline version/preview at existing source maxima cannot traverse the current draft path. U8 therefore proposes a separately typed, narrowly allowlisted read boundary with 192 KiB for both the complete callable response (including wrapper) and native re-encoded bridge packet, measured on both hosts. Existing draft/custom and protected command response limits remain intact. This is a real approval prerequisite, not already available capacity. Rejecting U8 requires a new decision: smaller aggregate publication content (for example a measured <=48 KiB complete version), or bounded-child reads/preview navigation with separately measured complexity. Neither content reduction nor multipart transport is assumed approved.

Recommend one document conditional on U8: the whole version is consumed together, storage/transaction limits fit comfortably, fewer reads/writes/index entries are required, and no child consistency/manifest invariant is added. Smaller child documents are unnecessary for Firestore storage limits but could help retain the old per-read transport ceiling. That alternative would need separately designed bounded preview reads before publication and extra detail navigation afterward; its read/confirmation protocol is not approved by this comparison. The old future schema diagram is not a requirement. The chosen document has bounded nesting (no more than six map/array levels), no independent item query, and no large text query. No chunking, blobs, staging, parallel journal or index exemption is necessary for this proposal.

Official limits checked 2026-11-02: document 1 MiB, request 10 MiB, field/map depth 20, index entry 7.5 KiB, 40,000 entries/document and 8 MiB indexed bytes/document. Indexed values over 1,500 bytes are truncated; do not query the copied arrays/instructions or treat those indexes as content checks. The 500 field-transform limit is not a generic 500-document transaction guarantee. See [Firestore quotas](https://firebase.google.com/docs/firestore/quotas), [storage formulas](https://firebase.google.com/docs/firestore/storage-size) and [automatic-index defaults](https://firebase.google.com/docs/firestore/query-data/index-overview#automatic_indexes).

This deliberately exceeds calculated 90-entry/90,005-byte combined output. The assumptions exclude unapproved deployed indexes, automatic indexing overrides and schema baggage; query/index behavior and actual changed-index accounting must be verified during implementation. The script models current documented whole-map/whole-array ascending/descending indexes as well as array-contains; it does not assume large values are unindexed. No checked-in index change or production-readiness claim follows.

### Finite operations and reads

Reuse the existing `programDraftRequests/{stableHash(uid)}` admission counter for all program actions: **120/minute shared**, one read/one write, at most three attempts. No additional independent rate allowance. Business transaction maxAttempts 3 and five-second elapsed checks at entry/before writes/reply follow PR 3. A five-second check is an application abort policy, not a guarantee that an SDK RPC returns in five seconds. Native timeout/cancellation is unknown outcome for mutations.

| Operation | Business reads / writes per attempt | Accepted document-JSON budget; response budget |
|---|---|---|
| Publication prepare/preview | 5 authority + root + optional entitlement + <=12 sources = **19 / 0** | 388 KiB; 192 KiB result |
| Publish with no receipt | config + 5 authority + receipt + root + optional entitlement + <=12 sources = **21 / 3** | 396 KiB read; <=180 KiB logical write JSON (160+16+4); 4 KiB acknowledgment |

Per-document checks: authority <=16 KiB each; config/receipt/entitlement <=4 KiB; validated root <=16 KiB; each source <=24 KiB; version <=160 KiB. Malformed oversized records can transfer before rejection; these are acceptance budgets, not transport denial-of-service bounds. The existing resolver's broad legacy inputs do not acquire a universal new read-byte bound from this proposal.

Add one admission read/write (<=1 KiB record) to every feature operation, including errors/replay. Thus Publish is **22 reads / 4 committed writes maximum** across admission and business work; at three attempts each, at most **66 document-read attempts / 12 write attempts**, not twelve committed publication effects. Auth lookup is outside these Firestore counts; no unbounded source queries, history scans or cleanup writes. The selected 21-read business maximum does not need an extra next-version read: transactional `create` enforces absence. Counter/path inconsistency aborts; it never overwrites a collision.

The script models all seven legacy proof families, full note/custom/draft forms and five compacted kinds including proposed publication. It includes duplicated command in pending/proof, resolutionStarted flags, prepared/proof/retired/departure states, maximum normal decision widths and all resolver outcomes. False replay flag is the larger JSON representation; true is shorter. The quoted maximum epoch intentionally overestimates the actual departure integer by two bytes. Firestore Timestamp itself stops at year 9999; the recovery millis-width model retains the existing broader validator bound conservatively. History fixtures are structural width models, not freshly validated server receipts. These models are **not** evidence that future new-kind Kotlin decoding or Android/Swift persistence works.

Implementation must serialize the **actual** prior envelope plus every prospective state using production Kotlin serializers, including retained history and preferred-workspace metadata, both resolution flags, each normal status/replay flag and resolver outcome, full proof, retirement and maximum departure marker. Require all to fit the existing 64 KiB plaintext limit and the same stricter **36,500-byte new-kind ceiling** used for drafts. Derive the production wrapper bound from its actual key identifier: Swift `181 + 8*ceil(n/3)` (slash escaping included), Android `108 + 4*ceil((n+16)/3)`. Verify actual native encoders/stores before issuance; random ciphertext sizes supplement rather than replace the bound. U8's read-only response allowance cannot be used for any protected request, pending record or proof.

As with draft admission, reject occupied pending/proof, switch-in-progress, offline grants/manifests/journal/upload/recovery payloads or consumed keys. Preserve the actual settled record and metadata unchanged. Extend the pending-work preference-write fence to publication so metadata cannot grow into reserved proof space. Admission is rechecked under native ownership locks immediately before persistence/issuance. Old records continue existing read-or-lock/recovery rules; an overlarge prior record refuses **new** Publish without deleting, truncating, compacting or migrating history to make it fit. Shortening program text does not materially shrink this hash-only command; present a protected-storage capacity limitation rather than misleading text-length advice.
